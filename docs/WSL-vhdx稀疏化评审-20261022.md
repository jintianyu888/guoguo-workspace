# WSL vhdx 稀疏化评审（2026-10-22）

> 起因：主公问「稀疏化，为什么压缩完以后慢慢又涨上去了」
> 交叉评审：deepseek-v4-pro（评审员 A）+ moonshot/kimi-k3（评审员 B），两份均跑完（outcome=ok）

## 一、三个必须分清的量

| 量 | 本机实测 | 含义 | 实测命令 |
|---|---|---|---|
| ① vhdx 逻辑文件长度 | 190,084,808,704 B = **177.03 GiB** | Explorer 里的「大小」，只增不减 | `Get-Item X:\WSL\Ubuntu\ext4.vhdx` |
| ② 已分配簇 / 实占 | = 177.03 GiB，**压缩比 1.0:1，零空洞** | NTFS 真正占盘的字节 | `compact /q X:\WSL\Ubuntu\ext4.vhdx` |
| ③ ext4 内部真实用量 | **152 GiB** | guest 真正在用的块 | `df -h /` |

→ **② − ③ ≈ 25 GiB 僵尸空间**：ext4 已标记 free，NTFS 仍替它留着已分配的簇。

## 二、「涨回去」的确切机制（两评审一致）

- ext4 挂载带 `discard`（在线 TRIM），guest 删文件时**确实在发** UNMAP。
- 但 vhdx **当前不是稀疏文件**（`fsutil sparse queryflag` → "This file is NOT set as sparse"）。
- 非稀疏文件上，NTFS 不允许制造 deallocated range → **UNMAP 在 vhdx 层被吞掉，对宿主空间回收是 no-op**。
- 动态 vhdx 按 ~1 MiB 块分配宿主簇；ext4 分配器不保证复用最低空闲 LBA，
  「被写过的 LBA 集合」随时间**单调扩张** = 高水位。
- **压缩只清零这个高水位；日常使用又把它推回去。** 这就是"慢慢涨上去"。
- 补充（评审员 B）：即使开了稀疏，写 hole 会立即按需分配簇（回填）→ 稀疏控制的是**稳态高水位**，不是"只降不升"。

**易混点**：`DisableDeleteNotify=0` 管的是 NTFS→NVMe 物理盘的 TRIM，跟「vhdx 文件内部能否出现空洞」是两回事。两个 TRIM 域被混为一谈，才会产生"链路都通了怎么没回收"的困惑。

## 三、本机当前状态（全部实测）

- `fsutil sparse queryflag` → **NOT set as sparse**
- `compact /q` → 190,084,808,704 字节存进 190,084,808,704 字节，压缩比 1.0:1
- `wsl --manage Ubuntu --set-sparse true` → 报错 `Wsl/Service/E_INVALIDARG`
  原文：「由于潜在的数据损坏，目前已禁用稀疏 VHD 支持。要强制发行版使用稀疏 VHD，请运行:
  `wsl.exe --manage <DistributionName> --set-sparse true --allow-unsafe`」
- guest 内 `fstrim.timer` → enabled 但 **inactive**，`ConditionVirtualization=!container was not met`（WSL 下永不触发）
- X 盘：总量 1907.7 G，空闲 **1580.9 G**，已用 17.1%

## 四、真正的增长主因（评审没看到、我实测出来的）

10-16 那次 `diskpart compact` 后 vhdx = **71.4 GiB**；今天实测 = **177.03 GiB**。
**6 天净增 105.6 GiB（17.6 GiB/天）**。其中：

- **72 GiB = `/home/j/.openclaw-trash/20261019-fast-experiment`**（10-19 fast 实验残留）
  - 2 × ~19.5 GB 的 `openclaw-2026-10-19T*.tar.zst`（fast 线实验归档，zstd 校验通过，Frames=1 完整）
  - 4 × ~9.2 GB 的 `.openclaw-backup-publish-*/archive.tar.gz.tmp`（发布残留 tmp）
  - `fast-snap/` 里 2 个 sqlite 快照（lcm.db 329 MB / openclaw-agent.sqlite 326 MB）
  - ⚠️ **这批在 NAS 回收站没有副本**（NAS 只有 `trash-20260930.tgz` 23.4 GB + 09-30 的 ubuntu tar + 两个 2.2 KB 空壳包）
  - ⚠️ **也不在每日备份范围**（备份仓 `/home/j/openclaw-backup-repo` 用 `git ls-files` 查无 trash 路径）
- 其余 ~33.6 GiB = venvs(21 G) / backup-repo(7.6 G) / .cache(6 G) / update-captures(3.7 G) 等真实增长

**结论：主因不是稀疏机制，是 72 G 实验残渣被停在 ext4 内的回收站 + 非稀疏 TRIM 失效留下的 25 GiB 僵尸。**

## 五、稀疏化值不值得做（两评审一致：不值得）

- 收益上限 = ① − ③ ≈ **25 GiB**，仅占 X 盘空闲的 **1.6%**
- 风险：`--allow-unsafe` 字面意思就是**绕过微软因"潜在数据损坏"而设的保护**；
  故障模式不是丢一个文件，而是**整个 vhdx 损坏 → 149 G /home 全灭**（单点）
- 旁证：`fstrim.timer` 在 WSL 下永不触发，说明整套 TRIM→回收链路在 WSL2 里本就是"不受支持"状态

**替代方案（按推荐度）**：
1. **先清 ext4 内的 72 G 回收站** —— 零风险、收益 72 G（是稀疏化收益的 2.9 倍），且清完后 ext4 used 降到 ~80 G，届时可回收上限变 97 G
2. **不折腾**：X 盘空闲 1580.9 G，僵尸 25 G 无关痛痒
3. **真要封顶**：每季度 `wsl --shutdown` + `diskpart compact vdisk`（**不带 unsafe 标志**，无 corruption 风险），涨回去再压一次
4. `--allow-unsafe` 序列：**只当最后手段**，必须先做 vhdx 字节级备份

### 触发判据（满足任一才动手）
- X 盘空闲 < 20%（约 380 G）— 当前 1580.9 G，未触发
- vhdx 实占 − guest 用量 > 50 GiB — 当前 25 GiB，未触发
- vhdx 实占 > guest 用量 1.5 倍 — 未触发

### 若将来真做，完整序列（评审共识）
```
wsl --shutdown
wsl --manage Ubuntu --set-sparse true --allow-unsafe
fsutil sparse queryflag X:\WSL\Ubuntu\ext4.vhdx      # 期望: set as sparse
wsl -d Ubuntu -u root -- true
sudo fstrim -av                                        # 期望: trimmed 数十 GiB 量级
wsl --shutdown
diskpart: select vdisk file="X:\WSL\Ubuntu\ext4.vhdx" / attach vdisk readonly / compact vdisk / detach vdisk
# 验证
compact /q X:\WSL\Ubuntu\ext4.vhdx                      # 压缩比应 >1.0
fsutil file queryallocatedranges X:\WSL\Ubuntu\ext4.vhdx # 应出现大段空洞
wsl -d Ubuntu -e df -h /                                # 数据完整
```
回滚：`wsl --manage Ubuntu --set-sparse false`；已损坏则用事前备份整文件覆盖。

### 附：fstrim.timer 在 WSL 失效的修法（评审员 B 提）
```bash
sudo systemctl edit fstrim.service
# [Unit] 下写 ConditionVirtualization=   (清空条件)
sudo systemctl enable --now fstrim.timer
```
或用 Windows 计划任务每周跑 `wsl -d Ubuntu -u root fstrim -av`（更稳，避开 WSL 空闲自动关机）。

## 六、风险提示
1. `--allow-unsafe` 绕过的是数据损坏保护，坏了就是整盘报废
2. compact 必须全程 guest stop，中途断电可能让 vhdx 不一致
3. fstrim 在 WSL 无自动定时，开稀疏后必须手动/计划任务补，否则照样涨回去
4. 未做字节级备份前，禁止执行 set-sparse
5. **回收站的副本不在 NAS、也不在每日备份里** —— 清理前必须先在 E/H 盘留一份
