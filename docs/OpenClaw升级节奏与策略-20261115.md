# OpenClaw 升级节奏与升级策略（2026-11-15 定）

数据源：npm registry `openclaw` 全量 297 个版本（稳定 132 / 预发布 165，2026-01-29 起）+ GitHub releases 说明体量。
统计脚本口径：按 稳定版（无 beta/rc）时间戳。

## 一、实测节奏

- **新功能线**：每 25~37 天开一条（10-11 开 2026.10、11-05 开 2026.11，间隔 25 天；前几条 28~48 天）。
- **功能版 vs 补丁版**：每条线的 `.1` 是功能版，发布说明特别长（2026.11.1 正文 21KB；补丁版 11.2 4.6KB、11.3 7.1KB）。9.33 25KB、10.1 20KB 同理。
- **同线补丁**：中位间隔 53.5 小时（≈2.2 天），一条线通常出 5~10 个补丁。
  - 2026.10 线：10 个补丁 / 23 天，其中 0-7 天 4 个、7-14 天 3 个、14 天后 3 个。
  - 2026.11 线：11.1(+0) → 11.2(+3.0d) → 11.3(+5.3d)，目前 3 个。
- **版本存活期**：一个版本作为 latest 平均只活 75.8 小时（中位 53.5 小时）。
- **旧线维护**：`extended-stable` 现在是 2026.9.37（11-11 发布，与 11.3 同天）——旧功能线继续收安全补丁约 2 个月。

## 二、主公的判断对不对

「先加功能，然后几个补丁修 bug，再隔一阵加功能」——**基本成立，但对"安静期"要修正**：

1. 功能版集中在每线第一版，之后全是补丁，这点对。
2. 但线内**几乎不存在长时间安静**：补丁中位 2.2 天就来一个，等"完全没新版本"往往要等到下一条功能线前夜，那时又要被新功能顶掉，等于永远不升级。
3. 真正稳定的时机不是"没补丁"，而是"**本线最恶劣的回归已经暴露并被修掉**"——经验位置在首版后 7~10 天：此时该线 60~75% 的补丁已经出完。

## 三、策略（已落地为工具判定）

1. **beta / rc 一律不碰**（当前 beta=2026.11.5-beta.2）。
2. **一条线只升一次**：升级目标 = 首版后 7~10 天时的最高补丁版；升完就冻结该线，线内后续补丁不追。
3. **静默门槛**：目标版本发布 ≥7 天（`--soak` 可调）才动手；新补丁一出现，静默计时清零。
4. **不把 extended-stable 当升级目标**：它是更老的功能线（9.x），只作应急回落参照。
5. **安全补丁例外**：发布说明出现明确安全修复时可提前升级。

按此策略，节奏约 **每月一次**，常态落后 latest 2~3 个补丁（1~2 周），换掉的是"追版本踩回归"的风险。
