## 1. 飞书渠道 / 管家连接（多应用）

### 1.0 架构前提
- **一个飞书自建应用 = 一个机器人** ⇒ 每个管家单独建应用，各一套 `App ID + App Secret`。
- 配置：`channels.feishu.accounts.<账号名>`；绑定：`bindings` 加 `{agentId, match:{channel:\"feishu\",accountId:\"<账号名>\"}}`。
- 标准字段：`enabled:true` / `appId` / `appSecret`(SecretRef) / `connectionMode:\"websocket\"` / `dmPolicy:\"allowlist\"` / `allowFrom:[该应用下的用户id]`。

### 1.1 ⚠️ 症状：账号 connected，消息进来却「没人回」
- **根因（2026-10-01 真凶）**：**飞书 open_id 每个应用各不相同**！同一 owner 在 A 应用是 `ou_4e21…`、在 B 应用是 `ou_5ede…`。跨应用复制 id ⇒ `dmPolicy=allowlist` 把 owner 当陌生人挡掉。
- **一眼定位**：
  ```
  journalctl --user -u openclaw-gateway --since '20:00' | grep feishu
  → feishu[health-self]: received message from ou_4922…            ← 其实进来了
  → feishu[health-self]: blocked unauthorized sender ou_4922… (dmPolicy=allowlist)
  ```
- **解法**：从日志抓该应用视角的 open_id → 写进**该账号**的 `allowFrom` → **重启网关**。
  ```
  journalctl --user -u openclaw-gateway --since '20:00' --no-pager \\
    | grep -oE 'feishu\\[<账号>\\]: received message from ou_[a-f0-9]+'
  ```
- **教训**：allowFrom「一应用一份」，禁跨应用复制。

### 1.2 症状：connected，但日志连 `received` 都没有
- **根因**：应用没配**事件订阅**（或订阅方式不是长连接）。
- **解法**（飞书开放平台，逐应用）：①「添加应用能力」勾 机器人 ②「事件与回调 → 事件配置」订阅方式＝**使用长连接接收事件** ③ 添加事件 **`接收消息 v2.0`（im.message.receive_v1）** ④ 权限 `im:message`、`im:message:send_as_bot` ⑤ 发布/启用。
- **注意**：**权限 ≠ 事件订阅**，两个开关；日志里 `ignoring stale permission scope error: contact:contact.base:readonly` 可忽略。

### 1.3 新增管家接飞书的标准流程
1. 收 **App ID（明文）** + **Secret（加密框，进密钥库）**
2. 写 `channels.feishu.accounts.<id>`（appSecret 用 SecretRef）
3. 加 `bindings`
4. **重启网关**
5. **自证**：`openclaw channels status` 出现 `<id>: running, connected`；让 owner 发一句看日志；被 blocked → 按 1.1 补 id → 再重启

### 1.4 现状（2026-10-01）
- 老 5：`default`(main)/`mom`/`script-mystery`/`print`/`sheet-music`
- 新 6：`class-schedule`/`health-wife`/`health-self`/`news`/`cooking`/`calendar`（前 5 个已按各自 open_id 修好；**calendar 待抓 id**）
- 未接 9：`doll-brand`/`fitness`/`health-doudou`/`health-wang`/`piano-app`/`piano-room`/`schedule-doudou`/`tax`/`wealth`
- 明确不接：`doudou-apply`/`health-jin`/`mail_reader`

## 2. 网关重启与服务

### 2.1 症状：`restart` 卡在 `deactivating`/`stop-sigterm`
- **根因**：网关 shutdown 没走干净（稳定性日志 `gateway.restart_close_failed`「Gateway shutdown did not complete cleanly」/`restart_shutdown_timeout`）。
- **解法**（越线，需 owner 授权 + 记 `state/security-alerts.md`）：`systemctl --user kill -s SIGKILL openclaw-gateway; sleep 2; systemctl --user start openclaw-gateway`
- **副作用**：重启会打断当前那轮会话（提示 `previous turn was interrupted by a gateway restart`）→ 按提示「查状态→续做」。

### 2.2 重启规矩（owner 2026-09-27 定）
- 先发飞书预告（为什么＋预估耗时）→ 等 20–30 秒 → 执行 → 恢复后发「已恢复」。
- 优先用系统工具 `openclaw`（gateway.restart）；工具不可用时才走 shell（须授权）。

## 4. 备份与恢复

### 4.1 症状：归档失败 / 监控报「N 小时没备份」
- **根因 A（脚本层）**：`backup-retain.sh` 用了 bash 专有语法，却被 `sh`（dash）调用 ⇒ `Syntax error: redirection unexpected`，**每次备份都报错**。
  → **解法**：改成 `bash` 调用（或改写为 POSIX 兼容）。**排查手法**：`grep -rn 'sh .*\\.sh' tools/` 找出所有用 `sh` 调用的脚本，逐个 `sh -n` 验证。
- **根因 B（路径层）**：归档落点从 `/home/j/Backups` 迁到 `/mnt/d/openclaw-backups`，但监控还在看**旧路径** ⇒ 假告警。
  → **解法**：监控改为「两处取最新」；**规矩：改落点必须同步改监控**。

### 4.2 🔴 `.ssh` 私钥从未进备份（审计发现的最严重项）
- **根因**：全量归档只打 `/home/j/.openclaw`，`.ssh` 在 `/home/j` 下被整个漏掉（实测 tar 顶层条目数=0）。**本机磁盘全毁连 NAS 归档都取不回**（访问群晖的钥匙）。
- **解法**：`gpg --symmetric --cipher-algo AES256` 加密成 `backup-extra/ssh-backup-*.tar.gz.gpg`，口令存 `/home/j/.ssh-backup-PASSPHRASE.txt`（600）＋**抄到外部**（手机/密码管理器）。
- **验证口令（必做）**：
  ```
  PASS=***; gpg --batch --yes --decrypt --passphrase "$PASS" -o /tmp/x.tar.gz <加密包>
  tar xzf /tmp/x.tar.gz -C /tmp/x && sha256sum /tmp/x/.ssh/id_ed25519 /home/j/.ssh/id_ed25519
  # 两个 sha 一致 ⇒ 可恢复；验完立即 rm -rf /tmp/x
  ```
- ⚠️ 注意：`*.enc` 那种旧产物**不是 gpg 格式**，别拿它验；真包是 `*.tar.gz.gpg`。

### 4.3 L2 git 推送失败（非快进冲突）
- **根因**：本地 auto-mirror 与群晖 workspace-backup **各有分叉提交**。
- **解法**：`git fetch origin && git -c user.name=openclaw -c user.email=openclaw@local pull --rebase origin master && git push origin master`
- **红线**：禁 `--force` / `reset --hard` / `clean` / 删分支；身份用一次性 `-c`。

### 4.4 管家原始 sqlite 归档不全（3/22）
- **解法**：`tools/stage-agent-dbs.sh`（备份前把 22 个 `agents/*/agent/openclaw-agent.sqlite` 压缩进 `backup-extra/agents-db/`），接入 `nas-push-archive.sh`。自证：`ls backup-extra/agents-db | wc -l`（应 25）。

### 4.5 新增管家没进 git 镜像
- **症状**：新管家工作区**没有 `.git`** 或**没配 remote** ⇒ 不在 L2 镜像层。
- **解法**：`git init` → 提交 → 群晖 `git init --bare ~/ws-workspace-<名>.git` → `git remote add origin ssh://jintianyu@192.168.1.5/volume1/homes/jintianyu/ws-workspace-<名>.git` → push。
- **自证**：22/22 都有 `.git` + remote；群晖 `ls -d ~/ws-workspace*.git | wc -l`。

## 5. 存储 / 磁盘

### 5.1 `/tmp` 是 RAM 盘（9.8G），会被写满
- **症状**：`No space left on device`、tar/pip 失败、SQLite 「database or disk is full」。
- **解法**：① 大件一律落 `state/dl/`（磁盘），别用 `/tmp` ② `tools/tmp-watch.sh`（>80% 告警、>92% critical）接入每日自检 ③ 清 `pip` 解包目录、`.part*`、>1天旧文件。

### 5.2 D 盘满 / WSL 虚拟盘只增不减
- **背景**：WSL 的 `ext4.vhdx` 只长不缩 ⇒ 删除文件不还 C/D 盘空间。
- **处置**：① 备份归档等**冷数据**可挪到别的盘（改 `nas-push-archive.sh` 的 `OUT`）② **「在用」的绝不挪**（如 WSL 虚拟盘本身，挪了掉速）③ 真缩需 `wsl --shutdown` + 导出/导入迁移。
- **纪律**：挪之前先 `df -h` + `du -sh` 摸清谁最占；挪之后**同步改脚本落点**。

## 7. 打印

### 7.1 设备：TOSHIBA e-STUDIO `192.168.1.80`
- `9100`：裸 PS 队列，**只认纯文字/矢量**；`631`：IPP（**定版主通道**）。

### 7.2 ⚠️ 血泪教训：9100 裸推**不渲染图像**
- **证据链**：#25 纯矢量 ✅ 出纸；#26 `image`+currentfile **静默不画**；#27 `imagemask` 同链 **stackunderflow**；#29 四路对照**全不出图**；#30 最老 Level-1 操作数写法**也不出图**。
- ⇒ **结论**：本机 PS 解释器**与压缩/滤镜/尺寸/写法都无关**，就是不执行 `image` 家族。**换 RLE / 取反 / 去 setcolorspace 一概无效**。
- **正解**：乐谱/图像 ⇒ **IPP 631 直投原始 PDF/JPEG**（设备自带引擎渲染），`tools/print-ipp.py`。

### 7.3 ⚠️ 禁 PJL（会把作业源码当文本打出来）
- **症状**：纸上印的是 `%-12345X @PJL JOB … %!PS-Adobe-3.0 …` 源码。
- **根因**：`print.py` 的 `prelude` 无条件生成 PJL（`use_pjl` 只约束了 `epilog`）。
- **解法**：`prelude`/`epilog` 都受 `use_pjl` 约束，且 **`use_pjl = False` 硬编码**（这台机器不吃 PJL）。自证：`grep -n 'prelude' print.py` 看是否 `if use_pjl else b\"\"`。

### 7.4 ⚠️ 禁 `setpagedevice`
- **症状**：纸上只有一行 `PS error: undefined`，其余空白。
- **根因**：本机 PS 对 `<< /PageSize […] >> setpagedevice` 报 undefined（PJL-free 的 #17/#18 实物即此症状）。
- **解法**：生成端不发 `setpagedevice`；纸型交给纸盒/面板（DSC `%%BoundingBox` 即可）。

### 7.5 「一张纸出两份」
- **根因**：`print.py` 只在给了 `--paper/--duplex` 时才发 PJL；不给时**不发 PJL**，打印机就用**自己的默认份数**（这台默认 2 份）。
- **解法**：强制 1 份（`@PJL SET COPIES=1` 或 PS `<< /NumCopies 1 >> setpagedevice`）—— ⚠️ 但本机禁 PJL/setpagedevice，故**优先 IPP**（IPP 默认 1 份）。

### 7.6 「复跑验证」导致重复投递
- **教训**：投递类操作**复跑 = 真投**！验证请用 `--dry`。2026-10-01 就因此多打了一张（台账 #35/#36 同 sha）。

### 7.7 找附件要去**对应管家的工作区**
- 主 `workspace/media/inbound` 里可能是**证据照**（例如乱码纸照片）；真乐谱图在**打印工作区** `workspace-print/media/inbound`。

## 14. 权限与放行流程

- **owner 2026-10-01 令：所有权限申请统一找果果**。
- **低风险**（本机既定脚本用途、读自己工作区、本领域资料整理写入本工作区）⇒ 果果**直接放行 + 事后报备**。
- **高风险**（花钱 / 删数据 / 对外发送 / 开权限给他人 / 改渠道结构 / 密钥 / gateway 结构与插件安装）⇒ 果果汇总后**只问 owner 一句**。
- **越线操作**（如 SIGKILL 重启网关）必须 owner 明确授权 + 记 `state/security-alerts.md`。

## ⚠️ 2026-10-01 新增：**别把管家工作区挪出 WSL 文件系统（血的教训）**

### 症状
给管家发消息报：
```
workspace path alias points to a different current target:
  /home/j/.openclaw/workspace-<x> now resolves to /mnt/e/.../workspace-<x>,
  but its stored workspace state belongs to /home/j/.openclaw/workspace-<x>.
Run `openclaw doctor --fix` and confirm the move
```
⇒ 管家**认不出自己的家，全部罢工**。

### 根因
- OpenClaw 为每个 agent **持久化记录 workspace 路径**；把目录换成**软链**（指向 /mnt 的 Windows 盘）后，**解析目标与记录不符** ⇒ 拒绝运行。
- 而且 `/mnt/e` 是 **9p 挂载**：即使绕过校验，管家读写也会**变慢**、git 可能异常。
- ⚠️ `openclaw doctor --fix` **在网关进程树内跑不了**（报 `This command is running inside the gateway process tree … cannot safely manage the gateway that owns it`）。

### 解法（回滚）
```bash
for W in /home/j/.openclaw/workspace-*; do
  [ -L "$W" ] || continue
  n=$(basename "$W"); SRC="/mnt/e/openclaw-work/$n"
  rm -f "$W" && cp -a "$SRC" "/home/j/.openclaw/$n"
done
# 校验：symlinks=0, realdirs=22
```

### 教训
1. **管家工作区必须留在 WSL 原生 FS**（即 vhdx）；想省 D 盘空间，**别打工作区的主意**。
2. 挪之前先算「收益 vs 代价」：22 个工作区**总共才 ~545M**（D 盘已用 468G），挪了收益≈0，代价=**全系统罢工**。
3. 真正能省 D 盘的是**冷数据**（备份归档 109G），那类可以挪（且已在挪）。
4. 挪任何东西前，**先拿 1 个做试验**并**验证目标系统仍能识别**，再批量。

## 抖音下载：yt-dlp 报 "Fresh cookies needed" ≠ cookie 过期（2026-10-09）
