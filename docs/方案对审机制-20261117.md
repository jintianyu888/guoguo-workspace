# 方案对审机制 v1.0（2026-11-17 主公问询后定）

## 结论
要审，但不是所有方案都拉 5 个人审。按影响面分三级，只审该审的，且每位评审必须交「一个具体失败点」，不许写「同意」。

## 三级（按影响面，不按方案重要性自评）
- L1 小改（可回滚、影响 ≤1 天、不跨管家）：不改流程，我做+入账+报备。例：批次1 四个空闲管家换模型。
- L2 跨面（模型分配、cron 时间表、成本策略、共享流程）：3 席对审，2/3 通过；席位按变更类型固定，不随机。
- L3 不可逆/花钱/对外（删除、发布、权限、升级、下单）：3 席旗舰 + 主公批准；主公可否决任何一条。

## 必答四问（写不出就不算评审完成）
1. 这条方案最可能怎么失败？给证据或场景，不许写「风险较高」。
2. 缺了哪个前置条件？没做的验证是什么？
3. kill 判据能不能机器判定？给命令。
4. 结论：合格 / 须改（列必改项）/ 否决（给替代方案）。

## 反形式化三条（吸取 11-15 互审教训）
- 5 个管家若同一个模型 = 同一个脑子，意见不一致才有信息量。评审席 provider 必须不同（同厂不同档不算）。
- 只看方案文本、不看真实数据的评审无效；评审必须至少跑一条命令核对。
- 无异议 ≠ 通过：写明「未发现问题」也要给一条验证过的检查项。

## 流程
1. 我写方案（含 kill 判据、回滚命令、验收命令）。
2. agent-msg.sh 投给 3 位相关管家，deadline 默认次日 09:00；超时记 timeout，不计入轮次。
3. 回收进 state/review/<主题>/loop.json，必改项改完重投，最多 2 轮。
4. 我出 3 行结论（必改项/未解分歧/我的建议）+ 主公批准。
5. 无定论 → 上交主公，绝不自判通过。

## 谁审什么（按变更类型固定席位）
- 模型分配/额度：model + backup + maint
- 备份/存储/删除：backup + maint + work
- 调度/cron/时间表：maint + work + model
- 打印/乐谱/外发：print + sheet-music + work
- 升级/重启/权限：maint + backup + model
