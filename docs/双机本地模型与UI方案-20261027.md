# 双机本地模型 / 界面 / iPad 扩展 方案（2026-10-27）

状态：草案 v0.1（待交叉评审）
作者：果果　评审轮次：第 1 轮（两家不同厂商）

## 1. 结论先行

1. **云端仍是主力执行者**，本地模型只承担「零成本巡检 / 短文本分类摘要 / 断网兜底 / GPU 专用小任务（ASR/OCR/人脸）」。
   原因：我的主会话常态 120K–150K 上下文 + 大量工具调用，本地 20B/30B 模型（16–32K 有效上下文）接不住，硬换会显著掉链子。
2. **两台机分工不同**，不要做成两台一样的：
   - **A 机（本网关机）**：网关大脑 + GPU 小任务（whisper/OCR/face）。升级后 64GB 双通道，主要收益是 **WSL 内存上限可提到 40–48GB** 和 **CPU 侧带宽翻倍**。
   - **B 机（主力推理机）**：9070XT 16GB + 9950X，是唯一能「整模型上 GPU」的机器 → **ollama 主力放 B**。
3. **gpt-oss:20b 确实适合做 B 机主力本地 Agent 模型**，但**不适合做我的主 Agent**；外部建议里「上下文 32K」这条不准确（原生 128K，实际受显存限制，落地按 16–32K 用）。
4. 本地不要堆到 3–4 个模型：**B 机保留 2 个（gpt-oss:20b + qwen3:30b-a3b）**，A 机保留 1 个兜底即可。
5. 界面：**先 PWA（≈0 成本）**，想要更好看再做单文件自定义面板（1–2 天）；打原生 exe 壳性价比低，不建议现在做。
6. 局域网访问 **已经可用**（网关 bind=lan + token），iPad 和局域网电脑现在就能开，不需要新开发。

## 3. 对外部建议的逐条复核

| 外部建议 | 判断 | 理由 |
|---|---|---|
| gpt-oss:20b 是 16GB 显存下的 Agent 首选 | **基本成立（但只针对 B 机）** | 21B MoE / 3.6B 激活 / MXFP4 ≈12–13GB，16GB 显存可整模型驻留；工具调用格式比 14B 蒸馏稳 |
| 上下文 32K | **不准确** | 原生 131072（128K）；ollama 默认 num_ctx=4096，可调。16GB 显存下现实按 16–32K 用 |
| 我（果果）的主模型换成 gpt-oss:20b | **不成立** | 主会话 120–150K 上下文 + 复杂工具编排，本地 20B 接不住；且中文自然度不如 Qwen |
| R1-Distill-14B 做推理参谋 | **不必装** | 云端 v4-pro 已是更强参谋；本地再加一个 10GB 模型只增负担 |
| Qwen3-Coder:14b 做代码专项 | **可选，优先级低** | 30b-a3b 已能写脚本；真要专用再加，避免模型堆叠 |
| 「主力 Agent + 专项辅助」的组合思路 | **成立** | 与我的实际用法一致，但执行者应是云端，本地是辅助 |

## 4. 双机分工

| | A 机（本网关机） | B 机（主力推理机） |
|---|---|---|
| 升级后硬件 | 8700G（不变）/ **64GB 双通道** / 3070 8GB | **9950X** / 32GB（16×2 双通道）/ 9070XT 16GB |
| 主职责 | 网关 + 全部管家 + 备份/监控/告警 + GPU 小任务（whisper、PaddleOCR、insightface） | ollama 主力推理（整模型上 GPU） |
| 本地模型 | 1 个兜底：**≤7B 小模型**（如 qwen3:8b）。**不用 20B**——8GB 显存装不下，只能大量 CPU 卸载，慢到没意义（评审采纳） | **常驻 2 个**：gpt-oss:20b（Agent/工具）+ qwen3:30b-a3b（中文长文/摘要）；qwen3:14b 仅按需不常驻；16GB 显存同时只驻留 1 个（keep_alive 调度） |
| 升级主要收益 | 内存 20→40–48GB（可把 9p 缓存、编译、venv 同时跑）；带宽 ×2 | 16C/32T + 64MB L3 + AVX-512：prompt 处理与 CPU 卸载段显著提速；GPU 可整模型 |
| 风险 | vhdx 非稀疏，内存放大后要盯 X 盘；换内存需 wsl --shutdown | AMD 卡在 **Windows** 上 ollama 的 ROCm/HIP7 栈是否认 gfx1201 需实测 |

## 6. 软件适配清单（落地动作）

1. **ollama 归属**：主力留在 B；网关侧 `tools/ollama-proxy.py` 增加「第二上游 = A 本机」的 fallback（B 休眠/关机时自动切 A 上的兜底模型），并保留 IP 缓存与 /24 扫描。
2. **B 机显卡验证（先决条件）**：在 B 上跑 `ollama run gpt-oss:20b --verbose`，看 `ollama ps` 是否显示 GPU 占比；若 Windows 侧 ROCm 不认 RDNA4 → 改在 **B 的 WSL 里跑 ollama（ROCm 7 / gfx1201）**，这是更成熟路径。此项必须实测，不能假设。
3. **模型拉取**：B 上 `ollama pull gpt-oss:20b`（约 12–13GB）。走 HF/ollama 镜像策略，避免长时间单连接断流（参考 stalled-large-download 经验）。
4. **keep_alive 策略**：兜底模型 `keep_alive=0`（用完即卸，避免占显存冲突 whisper/OCR）；B 的主力模型 `keep_alive=30m`。
5. **WSL 上限调整**：A 机内存到位后把 .wslconfig memory 20GB → **32GB 起步**（64GB 物理留 32GB 给 Windows，观察无抖动再谈 40GB）。**停机不能裸 wsl --shutdown**：按《重启铁律》走 tools/restart-gateway.sh --reason（内含预告），先备份，避开 04:00–06:05（评审采纳）。
6. **基准对比**：换机后 `bash tools/hw-bench.sh after --ollama` + `--compare`，产出「提升了多少」一页表，存档 `state/bench/`。
7. **纳入稳定性体检**：stability-check.sh 增加 3 项 —— ① 双通道是否生效（Windows 物理内存 2 条 + Channel A/B 都占用）② ollama GPU 占比 ③ 内存占用/交换阈值按新容量重算。
8. **模型准入**：任何本地模型进 fallback 链前，先跑 `tools/model-eval.py` quick 两题（既有规矩）。

## 7. 老 iPad 能干什么（按「旧 Safari 也能跑」排序）

1. **常驻墙面看板**（最实用）：全屏打开一个**纯静态单文件看板**（我生成 `state/portal/simple-dashboard.html`，只读 `/api/state` JSON，setTimeout 轮询，无框架），显示余额/备份/GPU/告警/待办。老 Safari 也能跑，比 Control UI 稳。
2. **随身对讲**：飞书 App DM 我，长按语音（本机 whisper 转写已就位）。
3. **乐谱阅读器**：乐谱管家出 PDF → iPad 全屏翻阅（考级/练琴场景，配合打印组）。
4. **菜谱/步骤台面屏**：烹饪管家产物全屏显示，做饭时免洗手翻页。
5. **打印前校对**：A4/A3 打印前在 iPad 上确认排版（省纸）。
6. **监控回看**：NVR 的网页/ISAPI 客户端在 iPad 上看。
7. **提词器 / 第二屏**：录制、讲解时用。
   限制：旧 iPad 的 Safari 版本老，Control UI 可能白屏 → 所以第 1 项做成零依赖静态页，兼容性最好。

## 8. 「exe / 好看界面」四种方案与代价

| 方案 | 效果 | 工作量 | token 量级 | 维护成本 |
|---|---|---|---|---|
| 0. 现状（bat + Edge 应用模式） | 无地址栏的类 App 窗口 | 已完成 | 0 | 0 |
| 1. **PWA 安装**（浏览器「安装为应用」） | 桌面图标 + 独立窗口 + 离线壳 | 0.5–1 小时 | ≈0 | 低 |
| 2. **自定义单文件面板**（HTML+JS 调 /api/state） | 真正好看、可定制，iPad/局域网通用 | 1–2 天 | 3–6 万 | 中（约 1 次/季度跟进 API） |
| 3. Tauri 原生壳（Rust，包住现有 UI） | 真 exe、系统托盘、开机自启 | 3–5 天 | 10–18 万 | 高（每次 UI 升级重打包 + Rust 工具链） |
| 4. 自研前端（React/Vue 全量） | 完全定制产品级界面 | 6–10 天 | 20–40 万 | 很高（长期跟进 API 变更） |

**建议**：先做 1（几乎免费），确认「够不够好看」；不够再上 2。3/4 只有在「要给外人用」时才值得。
说明：以上 token 为工程量级估算（含调试与返工），不是精确值；实际按每次评审/生成计费，flash 单价很低，主要成本是我的时间。

## 9. 局域网访问（现状与做法）

- 现状：网关 `bind=lan`，监听 `0.0.0.0:18789`，token 鉴权已开 → **局域网内任何设备现在就能访问**。
- 用法：`http://192.168.1.106:18789/`（首次需带 token 参数，token 存密钥库，不外传）。
- 安全：① token 只在自己设备保存；② 不做公网端口映射，外网访问走 **Tailscale**（本机已有技能与经验）；③ 建议后续给 Control UI 加只读访客模式，避免客人误操作。
- iPad/手机优先用第 7 节的静态看板（省 token、稳），Control UI 留给需要操作的场景。

## 11. 风险 / 待拍板

- **R1**：B 机 AMD 卡在 Windows 上 ollama 是否可用 GPU —— 需实测；兜底方案是在 B 的 WSL 内跑 ROCm。
- **R2**：A 机换内存需 `wsl --shutdown`（停机数分钟），需避开备份窗与静默窗，且**必须我发起预告后**执行。
- **R3**：64GB 后若把 WSL 上限抬到 40GB，vhdx 增长更快（非稀疏），需盯 X 盘水位（当前 18%）。
- **R4**：本地模型增加会占磁盘（gpt-oss:20b ≈13GB）；E 盘 35%、X 盘 18%，可放。
- 待拍板：① 是否按本方案落地 ollama 位置与模型清单；② PWA / 自定义面板做哪个；③ 换硬件后的停机窗口时间。

## 12. 交叉评审结论（2026-10-27 18:2x，两家不同厂商，均真跑完）

- **deepseek/deepseek-v4-pro**：GO-WITH-FIXES（约 4.3k 字）
- **MiniMax-M3.1-Flash-Preview**：GO-WITH-FIXES（约 0.9k 字）
- 两家均无否决，且都认可：云端主力 / 本地只做短任务 / B 机跑 ollama / A 机专做 GPU+兜底 / 界面先 PWA 不做 Tauri。

已采纳的必改项：
1. **A 机兜底模型降到 ≤7B**：8GB 显存装不下 20B，只能 CPU 卸载，慢到不可用。
2. **停机合规**：WSL 内存上限调整不能裸 wsl --shutdown，走 tools/restart-gateway.sh（内含预告）+ 先备份。
3. **上限先 32GB 不要 40GB**：64GB 物理下 40GB 会挤压 Windows 与网关自身，先观察。
4. **B 机同时只驻留 1 个模型**：16GB 显存不足以让 gpt-oss:20b 与 qwen3:30b 同驻，必须用 keep_alive / 按需加载调度。
5. **B 机设「插电不自动休眠」**：兜底只在 B 醒着时有意义；B 休眠时主会话能力必然降级（本地只救巡检/摘要类）。
6. **表述修正**：「只留 2 个模型」实为「常驻 2 个 + 按需 1 个」，已改。

未采纳（评审判断有误，已核实）：
- 「gpt-oss:20b 原版 fp16 约 40GB，16GB 装不下」——不成立。该模型 MoE 权重原生 MXFP4（4bit），ollama 拉取约 12–13GB，16GB 显存可整模型驻留（KV 留 2–3GB，现实上下文 16–32K）。判据是实测 ollama ps 是否显示 GPU 占比 100%。
- 「9950X 纯属浪费」——不归我改：CPU/主板是主公既定采购。我只如实说明：对 ollama 推理增益有限（瓶颈在显存与内存带宽），对 A 机侧无影响。
