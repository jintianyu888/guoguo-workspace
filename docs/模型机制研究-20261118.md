## 三、发现的四个机制问题

### 1. 45% 规则的口径错了（假绿根因）
model-compliance-check.py 用「主模型=某厂 的管家数 / 总管家数」判 45%。管家数与流量无关：24 个管家 7 天零任务，怎么分布都不产生调用。
改法：**主判据换成「近 7 天调用数占比 ≤45%」**，管家个数作辅助指标；花费占比只做展示（付费厂天然偏高，不作硬阈值）。落地工具 tools/model-pool-model.py，越线 rc=2。

### 2. kimi 残余 7 处（不是 0）
compliance 报「kimi 残留引用 0」只扫了管家的 primary，漏了 fallback 与 cron：
- agents.defaults.model.fallbacks[2] = kimi-coding/kimi-for-coding（38 个管家共用的兜底链）
- cron 首选 kimi：每日任务体检(08:35) k3-256k、管家每日自审-model、互审定稿-model、维护管家-周度盲区1900
- cron fallback 含 kimi：管家每日自审-maint、周计划(周日21:35)
证据：journal 里 429 行按厂统计 — kimi 297 行、zai 119、deepseek 46、qianwen/minimax 0；11-16 起 kimi 每日 58/139/99 行，全部是「先 429 再 failover 到 deepseek」。

### 3. 千问到期风险面比台账记的宽
台账只记「7 个管家待迁」。实际还有 10 个 cron 引用千问：6 个在 fallback 末位（到期后少一跳），1 个（互审定稿-work）**千问首选 + fallbacks=None**（到期直接失败），其余为首选/回退混用。
迁移工具 model-migrate-1201.py 原先把 2 个管家分给 deepseek（会把 86% 推到 90%+），已改为一律 zai/minimax 轮转。

### 4. 池子的真实结构是「一家独大 + 一家闲死」
deepseek 承担 86% 调用，minimax 周额度仅用 4%。这不是分配表写错，是**流量没被导过去**：分配按管家个数均摊，而实际产生调用的是少数 cron 与 main 会话。要改结构必须动「产生调用的那几个 job/会话」，不是动闲置管家的字段。
