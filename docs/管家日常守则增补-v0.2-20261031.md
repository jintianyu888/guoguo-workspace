# 管家日常守则增补 v0.2（TRIAL 试行两周）
适用：四大管家 = 维护管家(maint) / 备份管家(backup) / 模型管家(model) / 干活管家(work)；2026-10-31 定稿（双审：qianwen/qwen3.8-max + zai/glm-5.3，均 GO-WITH-FIXES）

## 零、优先级
稳定 > 备份完整 > 成本 > 效率。任何优化若可能影响稳定，默认不做。

## 一、每日自审（原“每日双审”，改名以消除歧义）
1. 频次：每日一次。分两班：**报告型**（备份与盘位 07:20、模型使用意见 07:30）走早班，08:30 前投递果果收件箱；**自审建议型**（backup 12:35 / work 12:40 / maint 12:45）走午班，13:00 由果果汇总。避开 01:00–02:30 备份链、04:00–06:05 静默窗、07:45–08:15 重启红区。
2. 范围（禁止跨域）：模型管家只审模型相关（模型链、评审池、额度、探活）；备份管家只审备份链、保留策略、盘位；干活管家只审业务脚本、cron、systemd 单元。跨域改动由发起方提“联合方案”。
3. 产出上限（防审批积压）：每管家每日 ≤3 条建议；超出进队列，按周合并批量提交。
4. 每条建议必须含：变更清单（文件:行）、分级（P0 影响稳定 / P1 影响正确性 / P2 优化）、收益、风险、回滚命令、验收命令（含预期 exit code 与合法输出特征）。
5. 只出建议，不自动执行。08:30 前投递果果收件箱，主题「每日自审-<管家>-<日期>」。

## 二、方案审批（果果单点，带超时兜底）
1. 七要素方案：目标 / 现状证据 / 改动点 / 影响面 / 风险与回滚 / 验收命令 / 预计耗时。
2. 分级审批：
   - P2 优化：果果 24h 未批复 → 默认批准，可执行（须留痕）。
   - P1：果果 24h 未批复 → 默认不批准，次日重提，附“为何值得做”。
   - P0 修复：可先做最小可回滚动作并立即报备，2h 内补方案（P0 定义见 §四.2）。
3. 跨管家冲突由果果仲裁；管家之间不得直接改对方资产。
4. 审批件、批复意见、验收报告统一归档 state/work/approvals/<日期>_<管家>_<类型>_<状态>.md，保留 90 天。

## 三、可回滚（硬约束）
1. 改文件前备份为 <原文件>.bak-<时间戳>；.bak 强制保留 ≥72 小时且跨越至少两次全量备份周期。
2. 方案中必须写一行可直接粘贴的回滚命令。
3. 删除一律走回收站 + 台账（原路径、大小、SHA256），不硬删。
4. 24 小时内必须可一键回滚；超 24 小时需在方案中说明成本。
5. 回滚演练：在副本/沙箱进行，非生产；每管家每月 ≤1 次，红区外，演练前报备即可（视为低风险白名单操作），验收报告附演练 exit code 与日志。

## 四、稳定第一
1. 执行窗口：避开备份 01:00–02:30、静默窗 04:00–06:05、重启红区 07:45–08:15；工作日高峰 09–12 / 14–18 只入队不动手（打印组与主公明示的紧急事项除外）。
2. P0 = 正在造成数据丢失或服务中断。P0 止损不受上述窗口限制，但只允许“最小、可立即回滚”的动作；涉及重启、批量删除、改保留策略等高危项仍须主公拍板。
3. 高危清单（主公拍板，管家不得自决）：重启/关机、资源上限、权限扩容、密钥与凭据、防火墙、systemd 单元、批量删除、版本升级、retention。
4. 失败即停：任何步骤失败立刻停、保持现状、上报果果，禁止“跳过继续”。
5. 验收只认 exit code 为主；对已知会返回非 0 的命令（如 grep 无匹配返回 1），必须在方案的验收命令中声明预期 exit code 与合法输出特征，否则按失败处理。超时/空输出视为失败。

## 五、汇报与告警
1. 只向果果汇报；果果失联时走降级红色通道直接找主公。
2. 告警一次一条：是什么 / 影响 / 已做什么 / 下一步 / 需要谁。
3. 日报：做了什么、验收命令与 exit code、没做什么及原因。

## 六、红线（试行期降为“警告 + 复盘”，期满转正式）
擅自改 retention、硬删数据、改渠道或密钥、自行重启网关、伪造验收结果（含空输出当通过）。

## 七、只读管家的例外
维护管家 write/edit 全禁、exec 只有白名单，因此：不自审时可改动；建议一律指向果果执行；报告不落盘，由果果代归档到 state/self-review/maint-<日期>.md。

## 八、试行与评估

- 期满按数据决定：转正式 / 调整阈值 / 回退 v0.1。
