## 1. 可行性结论（逐条对验收标准）

### 1.1 飞书群能让机器人收到群里发的文件吗？—— ✅ 能

官方文档《Receive message》（`https://open.feishu.cn/document/server-docs/im-v1/message/events/receive`）明确：

- 机器人收到用户/其他机器人发的消息时触发 **接收消息事件**（`im.message.receive_v1`）。
- 前提：①应用开启 **机器人能力（Bot capability）**；②在应用后台配置 **事件订阅**，订阅「接收消息」事件。
- 群内消息的推送，由应用的消息权限决定：
  - 只收群里 **@机器人** 的消息 → `im:message.group_at_msg`（旧）/ `im:message.group_at_msg:readonly`（含其他机器人版本另有 `...include_bot:readonly`）。
  - 收群内 **全部消息** → `im:message.group_msg.include_bot:read`（含其他机器人）/ `im:message.group_msg:readonly`（只收人发的）。
  - 收私聊给机器人的消息 → `im:message.p2p_msg` / `im:message.p2p_msg:readonly`。

> 实测佐证：`feishu_app_scopes` 返回 `default` 应用已授权 `im:message`、`im:message.group_msg`、`im:message.group_msg.include_bot:read`、`im:message.group_at_msg`、`im:message.group_at_msg.include_bot:readonly`、`im:message.p2p_msg:readonly` —— **收群消息所需的 scope 全齐**。

### 1.2 文件（图片/PDF/文档）能落到本机吗？—— ✅ 能，且已在发生

- 飞书消息类型含 `image`（图片，content 里带 `image_key`）与 `file`（文件，content 里带 `file_key`）、`media`（合并转发）、`post`（富文本内嵌图片附件）。
- 下载资源官方 API：`GET https://open.feishu.cn/open-apis/im/v1/messages/:message_id/resources/:file_key?type=file|image`（对应插件 SDK 的 `im.messageResource.get`）。
- **OpenClaw 飞书插件（@openclaw/feishu 2026.9.6）已实现自动下载**：源码（`monitor.account-D5j6WomE.mjs` 的 `resolveFeishuMediaList` + `saveMessageResourceFeishu`）显示，收到 `image/file/audio/video/media/post` 消息时，会按 `file_key`/`image_key` 调 `messageResource.get` 下载，并 `saveMediaStream` 存到 `~/.openclaw/media/inbound/<uuid>.<ext>`，然后把这个本地路径（`media.path`）交给 agent。
- 下载大小上限：`mediaMaxBytes = (channels.feishu.mediaMaxMb ?? 30) × 1MB`，即**默认 30MB**（可配置）。
- 发送侧官方限制（供参考，影响回发文件）：上传文件 ≤30MB（`im/v1/files`）、上传图片 ≤10MB（插件常量 `FEISHU_MAX_IMAGE_UPLOAD_BYTES=10485760`）。

**保存路径与保留时长（实测）**：
- 路径：`~/.openclaw/media/inbound/<uuid>.<jpg|png|...>`（文件名是 UUID，不保留原文件名；原文件名存在消息 content 的 `file_name` 字段里，插件已捕获）。
- 保留：目录里现有 115 个文件，最老 09-20、最新 09-25，即**至少保留了 6 天**。核心媒体存储有清理函数（`cleanOldMedia`），但源码注释明确「prune 不碰 inbound replay（入站回放）」，所以入站媒体**不会**被出站/转码缓存清理波及。**精确保留策略（是否按 TTL 清 inbound）未证实**，建议打印后不要依赖它长期留存，打印完即把结果登记进 print 管家的 `jobs.md` 台账。

### 1.3 打印 + 回话

- 打印：`tools/print.py --host 192.168.1.80 <file.pdf>`，9100 端口**已实测连通** ✅。
- 转换：Word/表格 → `tools/soffice-lo --headless --convert-to pdf`；图片 → `img2pdf`；扫描件 PDF → `tools/ocr-file`。三条链均「实测通过」（CONVERT-STATUS.md / OCR-STATUS.md）。
- 回话：飞书渠道回消息由 OpenClaw 通道负责（agent 正常回复即可，含回发文件 `im.file.create` / `im.image.create`，插件已实现）。

## 2. 两种接入形态对比

| 维度 | (a) 自建应用机器人（现成 default 应用） | (b) 群自定义机器人 Webhook |
|---|---|---|
| 能否进群 | ✅ 能（加进任意群） | ⚠️ 只在当前群生效，同一机器人不能进别的群 |
| 能否**收**消息/文件 | ✅ 能（事件订阅 + im:message scope） | ❌ **不能**，只能单向「推」 |
| 数据访问权限 | ✅ 有（im:message / im:resource 等） | ❌ 官方原文「custom robots do not have any data access rights」 |
| 能否下载文件 | ✅ `messageResource.get` | ❌ 无 |
| 审核 | 需租户管理员在后台配事件订阅/权限 | 免管理员审核（但因此无数据权限） |
| 适用 | **本需求唯一正确选项** | 只适合「果果主动通知」 |

> 结论：**只有 (a) 自建应用机器人能收文件**。群自定义机器人 Webhook 官方文档（`https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot`）已明确「单向推送、无数据访问权限、仅限当前群」，直接排除。

## 3. 落地步骤（可执行清单）

### 3.1 需要的权限 scope（已核实大部分已授予）

| scope | 用途 | 现状 |
|---|---|---|
| `im:message.group_msg` / `im:message.group_msg.include_bot:read` | 读群内全部消息 | ✅ 已授予 |
| `im:message.group_at_msg`（或其 readonly/含 bot 版本） | 读群内 @ 提及 | ✅ 已授予 |
| `im:message.p2p_msg:readonly` | 读私聊 | ✅ 已授予 |
| `im:message` / `im:message:readonly` | 拉取指定消息内容 | ✅ 已授予 |
| `im:resource` | 上传/下载文件、图片 | ✅ 已授予 |
| `im:message:send_as_bot` / `im:message` | 以机器人身份回消息 | ✅ 已授予 |

> 所以**无需老板再去后台申请任何 scope**（除非某账号配置时用了最小权限集，见 §6）。

### 3.2 订阅的事件

- **接收消息事件 `im.message.receive_v1`**（「消息与群组」分类下的「接收消息」）。
- 说明：现有渠道已能收到消息（inbound 目录 115 个文件即证），事件订阅**已生效**。

### 3.3 回调怎么配：WebSocket 长连接 vs webhook

- 当前配置**未显式写 `connectionMode`**，插件默认走 **WebSocket 长连接**（源码 `connectionMode ?? "websocket"`）。这也是推荐形态：**无需公网域名/IP，无需验签回调**，本机 NAT 后也能用。
- 若要 webhook（HTTP 回调），需要公网可达 + 配置验签，多一层麻烦，**无必要**。
- 结论：**保持默认 WebSocket，无需改回调**。

### 3.4 拿到群文件并触发打印的完整链路

```text
老板/太太在飞书群发图片/PDF
   → 飞书推送 im.message.receive_v1（WebSocket 长连接）
   → OpenClaw 飞书渠道：读 file_key/image_key
   → 调 messageResource.get 下载 → 存 ~/.openclaw/media/inbound/<uuid>.<ext>
   → 把 media.path 交到路由目标 agent（print 或 main）
   → agent 判断类型：
       图片 → img2pdf → PDF
       Word/表格 → soffice-lo 转 PDF
       扫描件 → ocr-file 出文字（可选）
       PDF → 直印
   → python3 tools/print.py --host 192.168.1.80 <pdf>   （A3/A4 自动选纸 + fit-to-page 不裁切）
   → 群里回话（已打印 / 已转 PDF / 需老板确认）
   → print 管家登记 jobs.md 台账
```

## 4. 权限与安全（机器人只给打印范围）

参照 print 管家现有 deny 列表做法，**机器人（路由目标 agent）应保持最小权限**：

print 管家当前已配置（`agents.entries.print`）：
- `tools.deny`: `edit`、`apply_patch`、`process`、`browser`、`computer`、`canvas`、`secrets`、`gateway`、`nodes`、`automations`、`sessions_spawn`、`sessions_send` ✅
- `tools.exec.mode: allowlist` ✅（只放行打印相关命令）

若决定路由给 print 管家，**这些安全配置已经就位**，只需确保 allowlist 里包含：
- `tools/print.py`（打印）
- `tools/soffice-lo`（转 PDF）
- `~/.local/bin/img2pdf`（图转 PDF）
- `tools/ocr-file`（OCR，可选）

**不要**给它：通用 shell、写工作区之外、gateway 配置、secrets、对外发送。

## 5. 绑定决策：飞书群消息路由给 print 管家 还是 main

### 结论：**建议路由给 print 管家**，main 做「入口 + 兜底」。

理由：
1. **职责单一**：收文件→打印是机械流水线，print 管家已有全套转换/打印/OCR 能力 + allowlist 安全壳，正合适。
2. **安全**：把「群里任何人发文件就触发打印」这件事圈在一个 deny 列表 + exec allowlist 的沙箱里，比放 main（总管，权限大）安全得多。
3. **省钱**：print 管家模型是 `qwen3.8-flash`（fast 档），机械活不进 main 烧主会话 token（这正是「输出纪律」里强调的主战场）。
4. **main 兜底**：老板要「找谱/整理/复杂判断」时，main 再介入。

### 配置改法（供老板批准后执行，本报告只给方案不改配置）

需要把飞书群消息路由到 print 管家。OpenClaw 的渠道路由靠 `bindings`（把某账号/某会话绑到某 agent）。当前飞书 `defaultAccount: default` 绑 main。具体改法（二选一，落地时再精确到字段）：

- **方案甲（推荐，按会话绑定）**：建飞书群后，把「该群的会话」绑定到 print 管家（`bindings` 里新增飞书群 chat_id → print）。main 仍处理私聊/其他群。
- **方案乙（按账号绑定）**：若想让 print 管家独占一个飞书应用账号（现有 `script-mystery` 或新开一个），把该账号绑 print。但会牺牲一个现有账号，且老板/太太要用哪个机器人进群要对应调整。

> ⚠️ 绑定字段的确切路径（`bindings` 结构、群 chat_id 的获取时机）需在落地时对着 `openclaw bindings` 文档确认，本报告不臆造字段名，**标未证实**。

### 群成员放行（`groupAllowFrom`）

飞书配置现有：
- `dmPolicy: allowlist`
- `allowFrom`: 4 个 `ou_...` open_id（老板/太太/相关人）
- `groupAllowFrom`: 同样的 4 个 `ou_...`

群消息 ingress 会校验 `groupAllowFrom`（源码日志「group ${chatId} not in groupAllowFrom」）。**需确认这 4 个 open_id 覆盖了老板 + 太太**；若王超的 open_id 不在列，要补进去。另注意 `groupAllowFrom` 的精确语义（是「群成员 open_id」还是「群 chat_id」）源码里混用了 chatId 与 sender open_id，**标未证实**，落地时以实测为准：若群里发消息没反应，先查这条。

## 7. 风险与坑

| 风险 | 说明 | 等级 | 备注 |
|---|---|---|---|
| 文件大小上限 | 上传/下载默认 30MB（`mediaMaxMb`）；图片消息单张 ≤10MB | 中 | 乐谱 PDF 一般 <30MB，够用；大文件需老板拆分或调大 `mediaMaxMb` |
| 图片转 PDF 分辨率 | `img2pdf` 无损嵌入原图，不重采样；打印清晰度取决于原图分辨率 | 低 | 手机拍照乐谱若糊，印出来也糊；必要时 OCR + 重排，但那是「找谱」范畴，不是本链路 |
| 频率限制 | 消息/资源 API 官方限流 1000 次/分 & 50 次/秒；事件推送频率官方未列明 | 低 | 家庭场景远达不到 |
| 多文件 | 飞书 `media`（合并转发）单条可含多文件；插件会逐个下载（`resolveFeishuMediaList` 返回数组） | 低 | 已支持，注意去重（插件有 dedupe key） |
| 群需 @ 还是全收 | 取决于群路由策略与 scope：`group_msg` 全收、`group_at_msg` 只收 @。当前 scope 两者都有，但 OpenClaw 群策略默认（provider 已配置时）`groupPolicy="open"`，`requireMention` 应为 false | 低 | 落地实测：不 @ 能不能触发，不能就补策略 |
| 审核/发布 | 自建应用若改动后台（事件订阅/权限），需走企业管理员发布审核 | 低 | 现状已生效，大概率无需再改后台 |
| inbound 保留时长 | 观察 ≥6 天，但精确 TTL 未证实 | 低 | 别依赖它归档；打印完登记 jobs.md，需要长期存就拷到 print 工作区 |
| 文件落盘是 UUID 名 | 原文件名在 `file_name`，插件已捕获并传给 agent | 低 | 打印台账里记原文件名即可 |
| 打印机 9100 原始打印 | 只能 PDF/PS/PCL 直印，非这些格式必须先转 PDF | 低 | 转换链已通 |
| 群路由/绑定字段路径 | `bindings` 结构与群 chat_id 获取时机未在本报告实测 | 中 | 落地时对文档确认，**未证实** |

## 8. MVP：30 分钟内跑通「群里发一张图 → 打出来」

> 前提：飞书渠道已连接（default 应用），打印链已通（已实测）。

**最短路径（约 6 步，多数已具备）：**

1. **建群 + 拉机器人**（老板操作，2 分钟）：飞书建群 → 拉老板 + 王超 + default 机器人。
2. **验证机器人能收**（2 分钟）：群里 @机器人 发「测试」，看是否回话 → 确认群路由通。
3. **确认放行**（3 分钟）：查 `groupAllowFrom` 是否覆盖王超 open_id；不在就补（这步可能要改配置，需老板批准）。
4. **路由给 print 管家**（5 分钟，需老板批准）：按 §5 方案把群绑到 print；或在 main 里临时手动代跑（不绑也能先验证打印）。
5. **发图实测**（5 分钟）：群里发一张图 → 查 `~/.openclaw/media/inbound/` 是否新增文件 → 确认已下载。
6. **转 PDF + 打印 + 回话**（10 分钟）：
   ```text
   img2pdf <新图.jpg> -o /tmp/x.pdf
   python3 tools/print.py --host 192.168.1.80 /tmp/x.pdf
   ```
   出纸 → 群里回「已打印 ✅」。

**MVP 验收 = 一张图从群里发出去，30 秒内打印机出纸，群里收到回话。**
