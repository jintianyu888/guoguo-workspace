# 模型分配方案 v1.0（2026-11-17 定 · 待主公批准批次）

## 一、要解决的问题（事实）
- 38 个管家，32 个（84%）主模型都是 deepseek/deepseek-flash。DeepSeek 一限流或欠费，32 个同时哑。
- kimi-coding 月度额度已用尽（429），但模型管家主模型仍是它，整晚在 fallback；它还挂在多处 fallback 链首位，白耗一次重试。
- 千问 Token Plan Lite 剩 93.4%，12-01 到期，13 天内不用就是白扔（含视觉能力）。
- 智谱 Coding Plan 已付费，5h 额度 0%、周 0%，还有 3 张未用的重置卡。
- MiniMax 额度宽裕；本地 ollama（B 机）免费但慢、且 B 会离线。

## 二、分配原则（先定规则，再排表）
1. 按活型定模型，不按喜好：重活要准、轻活要省、评审要跨厂、视觉要支持 vision。
2. 单厂不超过 45%；12-01 前故意把额度往千问倾斜（花掉即将过期的钱），但每个都配跨厂 fallback。
3. fallback 链第一顺位不能是死的：本周期全链撤掉 kimi-coding，恢复后再评估。
4. 本地 ollama 只做最后兜底，绝不做首选（慢、依赖 B 机在线）。
5. 改动必须可回滚：每次 patch 备份 + doctor 校验 + 不一致自动回改。

## 三、分层定义
- H 重活：正确性 > 成本（main / backup / tax / wealth / law / sheet-music / print / work）
- P 巡检：定时、只读、量大（maint / news / infoboard / security / calendar / project）
- C 生活对话：闲聊与查询，量大但轻（健康/日历/烹饪/学习等）
- V 视觉：要读图（model / library / maker）
- R 评审池：必须跨厂至少 3 家

## 五、分批执行（每批单独验收，失败即回滚）
- 批次 1（今晚，低风险）：english / study / chinese / useful → qianwen3.8-flash（4 个空闲管家，无定时任务）
- 批次 2（明天）：maint / news / infoboard / security → zai/glm-5.3-flash（先看 5h 用量再决定是否继续）
- 批次 3（明天）：视觉 3 个 + print（model / library / maker / print）
- 批次 4（后天）：main 与 backup 的 fallback 链清理（撤 kimi，加千问/ollama）
- 批次 5：剩余生活对话 13 个

每批动作：openclaw config patch --dry-run → 应用 → model-ledger.py sync-config → doctor → 抽查 1 个真实任务 → 入账。
回滚：state/backup/config/model-alloc-批N.json 反打，或按 ledger 里保存的上一版分配回写。

## 六、验收标准
1. model-ledger.py report 中单厂占比 ≤45%
2. 无任何 agent 的主模型或 fallback 首位指向 kimi-coding（本周期）
3. doctor 无「配置与台账不一致」
4. 连续 24h 无因模型导致的 429/超时堆积（model-health/status.json 无 down）
5. 智谱 5h 用量 <70%，千问 <90%

## 七、明确不做
- 不做按任务动态切换模型（现架构静态按任务定，动态切换引入不可归因故障）
- 不让模型管家改任何 agent 的 model 字段（只出提案，我执行）
- 不把 ollama 放首选
- 不在 12-01 之后继续让千问当默认（到期前必须有迁移动作，已登记在 promos 台账）
