## 二、分配原则（先定规则，再排表）
1. 按活型定模型，不按喜好：重活要准、轻活要省、评审要跨厂、视觉要支持 vision。
2. 单厂不超过 45%；12-01 前故意把额度往千问倾斜（花掉即将过期的钱），但每个都配跨厂 fallback。
3. fallback 链第一顺位不能是死的：本周期全链撤掉 kimi-coding，恢复后再评估。
4. 本地 ollama 只做最后兜底，绝不做首选（慢、依赖 B 机在线）。
5. 改动必须可回滚：每次 patch 备份 + doctor 校验 + 不一致自动回改。

## 三、分层定义
- H 重活：正确性 > 成本（main / backup / tax / wealth / law / sheet-music / print / work）

- V 视觉：要读图（model / library / maker）
- R 评审池：必须跨厂至少 3 家

## 十、更好的方法：池化 + 生成器（2026-11-18 13:40，已做成可用工具）

### 为什么改机制而不是继续排队分配
手改 38 个 agent 的 model 字段有三个结构性问题：换一次模型要改 38 处；审一次要审 38 行表；集中度靠人肉心算，算完还和现状不一致（评审已经抓到表里 36≠38）。

### 机制
- 真源 `state/model-econ/pools.json`：只写「几个池 + 谁属于哪个池」。池可以给 `rotation`（多个候选主模型，按成员稳定排序轮转）。
- 生成器 `tools/model-pools.py`：`--seed`（从现状生成）/ `--diff`（只显示差异）/ `--apply`（先备份再改配置）/ `--share`（按池算占比）。
- 人工只维护池；openclaw.json 是产物。改模型 = 改池一行 + apply。

### 三个池（当前）
- heavy 7 个（main/backup/tax/wealth/sheet-music/print/work）→ deepseek-flash，备 zai/glm-5.3 → minimax/M3 → ollama
- ops 3 个（有 cron 的其余）→ zai-flash / minimax / deepseek 轮转（禁千问，条款不允许 cron）
- daily 28 个（cron=0 纯交互）→ 千问 / zai / minimax / deepseek 四家轮转

### 生成出的占比（dry 计算，未应用）
- deepseek 15/38 = 39%｜zai 8 = 21%｜minimax 8 = 21%｜千问 7 = 18%
- **全部 ≤45%，四家在用**，且没有任何 cron 管家落在千问上 → 45% 这条从「做不到」变成「算得出来」

### 为什么 idle 管家可以随便分
28 个无 cron 的管家里 24 个 7 天以上零任务，分布到哪家几乎不产生调用；它们的作用是让占比结构合规，真正吃额度的是 heavy 那 7 个。
