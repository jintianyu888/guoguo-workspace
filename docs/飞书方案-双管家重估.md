# 飞书方案 · 双管家范围重估（print + sheet-music）

> 日期：2026-09-26 · 研究者：果果（子代理 feishu-plan）
> 性质：只读调研（未改配置、未重启、未装东西、未碰密钥/备份/NAS）
> 本文是 docs/飞书群打印方案.md 的范围补充与重估——老板把范围从「只有打印」扩到「打印 + 乐谱」两个管家。单管家可行性、下载落盘、scope、MVP 等基础结论仍以前文为准，本文只讲双管家的架构、路由、分工、权限。

---

## 0. 一句话结论

**建两个飞书群，按「群 chat_id」分别路由：打印群 → print 管家、乐谱群 → sheet-music 管家。** 源码已确认 bindings 的 match.peer 支持按群/会话 ID 精确路由，不是只能绑一个 agent。打印能力唯一归 print 管家；乐谱管家管收/找/归档/发谱，要打印时经 main 委派 print。

## 1. 一个群还是两个群？binding 能否按 chat_id 路由？

### 结论：两个群，且能按 chat_id 路由到不同 agent（源码已证实）

理由（两个群优于一个群）：
1. 权限天然隔离：打印是「收到文件就执行本地打印命令」的机械流水线，乐谱是「归档/编目/检索/发文件」的收藏管理——两个群给两个管家，各自的 deny 列表 + allowlist 互不干扰。
2. 职责单一、省钱：两个管家都是 qwen3.8-flash（fast 档），各自只干本职能，机械活不进 main。
3. 老板/太太心智清晰：想打印 → 丢「打印群」；想存谱/找谱 → 丢「乐谱群」。

### binding 按 chat_id 路由——已从源码证实

关键链路（OpenClaw 飞书插件 + 核心路由源码）：

- 飞书群消息进来时，插件 resolveFeishuGroupSession 计算 peerId：默认 groupSessionScope="group" → peerId = chatId（源码 default: peerId = chatId）。
- 然后调 resolveAgentRoute({ channel:"feishu", accountId, peer:{ kind:"group", id: peerId } })。
- bindings 的 match 支持 peer 字段：normalizeBindingMatch → normalizePeerConstraint(match.peer) → { kind, id }，且 matchesBindingScope 精确比对 scope.peer.id === match.peer.id。

即：一条 binding 可以精确绑定到某个群，写法是：

```json
{ "agentId": "print", "match": { "channel": "feishu", "accountId": "default", "peer": { "kind": "group", "id": "<打印群 chat_id>" } } },
{ "agentId": "sheet-music", "match": { "channel": "feishu", "accountId": "default", "peer": { "kind": "group", "id": "<乐谱群 chat_id>" } } }
```

当前配置只有两条通配 binding（main 兜底：feishu/accountId:* 和 wecom/accountId:*），尚无 peer 级绑定。落地时：保留 main 通配兜底（私聊/未匹配的群仍走 main）；在通配之前加两条 peer 级 binding（精确匹配优先于通配）。

> 待落地复核（标未证实）：match.peer 的确切字段名已从源码确认是 peer:{kind,id}，但 peer id 用的是群 chat_id（oc_... 开头）还是某种归一化 ID，需建群后取真实值核对一次；groupSessionScope 默认是 group，若后台改过 topicSessionMode/groupSessionScope 则 peerId 会变成「群+话题/发送人」复合 ID，影响绑定写法。默认未改则就是 chatId。

## 2. 若只能绑一个 agent → 统一入口选谁？

**结论：选 main（总管）做统一入口 + 分流**，而不是 print 或 sheet-music。

理由：
1. main 是「总管家」，本来就负责分派/汇总；sessions_spawn 能同时派给 print 和 sheet-music（两者 subagents.allowAgents 都含 main）。
2. print / sheet-music 都不适合当入口：print 权限太窄（deny 一堆 + exec allowlist），sheet-music 只懂乐谱。让它们当入口，要么越权要么漏活。
3. 分流逻辑：main 收到群消息 → 看「哪个群 / 消息类型」判断：文件要打印 → spawn print；乐谱/找谱 → spawn sheet-music。

> 但首选仍是 §1 的两群按 chat_id 直接绑定——比「main 分流」少一跳、响应更快、权限更干净。只有当按 chat_id 绑定落地遇到阻碍（如 peer id 语义不对、或想省掉两条绑定配置），才退到「两群都绑 main，main 分流」。

## 3. 两个管家各自的权限范围

### print 管家（打印）——已配好，基本不用动

当前 agents.entries.print：
- tools.deny: edit、apply_patch、process、browser、computer、canvas、secrets、gateway、nodes、automations、sessions_spawn、sessions_send
- tools.exec.mode: allowlist

放行范围（allowlist 只加这几项，别加通用 shell）：
- tools/print.py（打印，9100）
- tools/soffice-lo（Word/表格 → PDF）
- ~/.local/bin/img2pdf（图 → PDF）
- tools/ocr-file（OCR，可选）

明确不给：写工作区之外、gateway/secrets、对外发送、改他人配置、通用 exec。

### sheet-music 管家（乐谱）——当前无 deny 列表，需要补

实测 agents.entries.sheet-music 没有 tools 段（只有 name/workspace/agentDir/identity/model/subagents），意味着目前继承默认权限——比 print 宽。落地飞书群前必须补最小权限：

建议 deny（对齐 print 的安全壳）：
- process、browser、computer、canvas、secrets、gateway、nodes、automations

保留（乐谱职能需要）：
- read / write / edit / apply_patch（读写自己的 scores/ 与 scores/index.md）
- 消息发送能力（把谱文件作为附件发回老板）
- exec.mode：建议 deny 或 allowlist（乐谱归档/编目其实不需要跑 shell；若需要批量重命名/校验文件类型，再 allowlist 具体命令）。
- sessions_spawn：若要「乐谱管家直接委派 print 打印」，需放开给 print；否则关掉，打印走 main 中转。

红线（沿用 sheet-music AGENTS.md）：只发文件给老板本人、不对外分发、不编造曲目信息、不碰渠道/他人配置。

## 4. 乐谱管家 vs 打印管家的分工

| 职责 | sheet-music（乐谱群） | print（打印群） |
|---|---|---|
| 收乐谱文件 | 收纳到 scores/files/（保留原文件名） | — |
| 编目/索引 | 维护 scores/index.md | — |
| 找谱/检索 | 按曲名/作曲家/乐器/标签搜索引 | — |
| 发谱回老板 | 把谱文件作附件发回 | — |
| 打印 | 不自打印 | 唯一打印执行者 |
| 转换/OCR | — | soffice-lo / img2pdf / ocr-file |
| 收杂活文件打印 | — | 图片/PDF/Word/表格 → 打印 |

**核心原则：打印能力唯一归 print 管家，不在 sheet-music 复刻打印脚本。**
（避免两处维护同一套转换/打印逻辑，也避免权限扩散。）

### 乐谱群要打印时，调用链怎么走

三个选项，按推荐度：

1. **经 main 委派（推荐，改动最小）**：老板在乐谱群说「打印这份谱」→ sheet-music 定位到 scores/files/xxx.pdf → 把文件路径/内容交给 main → main sessions_spawn(agentId="print") 让 print 打印 → 结果回报。
   - 好处：符合「main 是总管家负责分派」的既有架构；sheet-music 不必开 sessions_spawn。
2. **sheet-music 直接委派 print（少一跳，但要开权限）**：给 sheet-music 的 subagents.allowAgents 加 print + 放行 sessions_spawn。
   - 好处：乐谱→打印快一步；代价：sheet-music 权限面变大（能直接驱动打印），需老板权衡。
3. **老板手动转发到打印群**：老板把要打印的谱转发去「打印群」。
   - 最原始但零配置，兜底可用。

> 建议先上「两群 + 方案 1（main 委派）」，跑顺后再决定要不要给 sheet-music 开直接委派（方案 2）。

## 5. 双管家 MVP（在单管家 MVP 基础上叠加）

1. 建两个飞书群：
   - 打印群：老板 + 王超 + default 机器人
   - 乐谱群：老板 + 王超 + default 机器人（同一个 default 应用机器人即可，两个群都加）
2. 群里各发一条 @机器人 消息，确认都能收到（拿到两个群的 chat_id）。
3. 补 sheet-music 的 deny 列表（§3）。
4. 加两条 peer 级 binding（§1），保留 main 通配兜底。
5. 实测：打印群发一张图 → print 管家打印；乐谱群发一份谱 → sheet-music 归档并回报。
6. 实测：乐谱群说「打印这份谱」→ 走 main 委派 print 打印。

**双管家 MVP 验收**：
- 打印群发图 → 打印机出纸，群内回话
- 乐谱群发谱 → scores/files/ 多文件 + index.md 多一行，群内回报
- 乐谱群喊打印 → print 管家执行、出纸
