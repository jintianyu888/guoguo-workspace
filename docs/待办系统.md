# 待办系统设计（2026-10-04）

## 为什么重构
旧做法：所有事都往 `state/pending-tasks.md` 一个文件里堆（已完成项、历史交接备忘、待办混在一起），08:00 提醒用模型去「读文件挑未完成项」→ 每次挑出的都不一样，已完成的事被反复提醒。**根因是数据与展示不分、无状态机、无归档。**

## 设计原则
1. **单一数据源**：`state/tasks/tasks.json`（唯一真相）。禁止手改展示文件。
2. **状态机**：每条待办是有限状态 `open → done/cancelled`，或 `open → paused`。
3. **归档制**：关闭的条目**移出** `tasks.json`，追加进 `state/tasks/archive.jsonl`（只增不删）。展示文件里永远不会出现已完成项。
4. **展示自动生成**：`state/pending-tasks.md` 由 `tasks.py render` 生成，只含未完成项。
5. **唯一 ID**：`T-YYYYMMDD-NNN`，编辑/关闭都按 ID，杜绝重复条目。
6. **零 token 提醒**：08:00 提醒直接跑脚本输出，模型不再「猜」哪些没完成。
7. **自检**：`tasks.sh check` 校验重复 ID、日期格式、已完成项残留、过期复查。

## 文件
| 文件 | 作用 |
|---|---|
| `state/tasks/tasks.json` | 数据源（未关闭项） |
| `state/tasks/archive.jsonl` | 已关闭项（追加，只增不删） |
| `state/pending-tasks.md` | 自动生成的展示（页脚/提醒/人看） |
| `tools/tasks.py` | 引擎（零依赖） |
| `tools/tasks.sh` | 包装器 |
| `tools/morning-brief.sh` | 晨间简报（待办+日程+时段，确定性） |

## 字段
`id` 唯一ID · `title` 一句话 · `detail` 详情 · `status` open/paused/done/cancelled ·
`owner` 主公/果果/管家id · `priority` P1/P2/P3 · `kind` decision/action/fix/research/maintenance ·
`created`/`updated`/`review`/`due` 日期(YYYY-MM-DD) · `source` 来源 · `tags` · `done_at`/`done_reason` · `notes`

## 用法
    tools/tasks.sh add --title "..." --owner 主公 --priority P1 --kind decision --review 2026-10-05
    tools/tasks.sh done T-20261004-001 --reason "已办"
    tools/tasks.sh cancel T-20261004-002 --reason "不需要了"
    tools/tasks.sh update T-... --review 2026-10-06
    tools/tasks.sh list --owner 主公
    tools/tasks.sh brief        # 晨间待办（确定性）
    tools/tasks.sh mine         # 我在办（页脚用）
    tools/tasks.sh render       # 重建 pending-tasks.md
    tools/tasks.sh check        # 自检

## 规则
- 任何新待办 → `tasks.sh add`（别手写 md）。
- 办完立刻 `done`（自动归档，展示里消失）。
- 每条 open 尽量有 `review`（下次复查日），避免无限期挂着。
- 展示文件 `pending-tasks.md` 只读，勿手改。
