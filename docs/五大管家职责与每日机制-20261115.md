# 五大管家职责与每日机制 v1.0（2026-11-15 主公令）

## 一、为什么要重做
现状盘点：维护/模型/干活/Hermess 四家**每天只有一个任务——自审自己**。备份只有「报告+自审」。也就是说：
- 管家的产出是"关于自己的报告"，没有对外交付物 → 典型空转
- 自审没有对照物，只能证明"我跑了"，不能证明"我干了"
- 汇总把 5 份自审拼起来，主公看到的还是"各家说自己正常"

新机制的出发点：**每个管家每天必须交付一件别人要用得上的东西**，自审只是附带。

## 二、职责边界（一句话版）
- 果果（main）：统筹、验收、汇总、闸门。不替管家干活，只做只读验收与升级。
- 维护（maint）：只读巡检 + 归因建议。不改系统、不落盘修复（只出建议，果果代执行）。
- 备份（backup）：备份产物看守 + 冗余度判断。只判"能不能恢复"，不管系统健康。
- 模型（model）：模型可用性/成本/路由结论。不碰音乐、不碰运维。
- 干活（work）：接主公临时活 + 队列清算。当天活当天了，不积压。
- Hermess（hermess）：乐谱/文档加工与归档。有活干活，无活说明为什么无活。

## 四、反空转机制（核心）
### 4.1 产出契约
`state/butler/contracts.json` 是唯一真源。每个每日动作必须写清四件事：**产物路径、最小字节、消费者、判据**。
写不出这四样的动作，一律不许排进调度。

### 4.2 机器巡检
`tools/butler-duty.py`（零 token）每天 12:30 跑一遍：
- 产物不存在 → ❌缺
- 产物 < 最小字节 → ⚠薄（说明是敷衍）
- mtime 不是当天 → ⚠旧（说明用了旧文件冒充）
- 三项全过才是 ✅

退出码非 0 就进 20:30 简报的红字区。

### 4.3 三档处理
- **连续 3 天 ❌** → 该动作降频（日→周）或停用；脚本给建议，我执行并记入账本
- **连续 3 天 ⚠薄** → 提示词加硬要求（点名具体数字），再不改善停用
- **产物连续 7 天没有消费者** → 合并或删除（没人看的报告 = 空转）

### 4.4 三类不许存在的动作
1. 只证明"我跑了"的动作（无产物）
2. 产物没人读的动作（无消费者）
3. 自审审自己的循环（自审必须对照外部事实：账本、盘位、调度状态）

## 五、当前状态与补齐计划
巡检 14 项契约，今日达标 8 项。缺口 6 项，分三类：
- **路径要修**：备份报告、备份自审（实际落在各自工作区，契约路径写错）→ 已修
- **今天还没到点**：20:30 简报（当天 20:30 才生成）→ 属正常
- **根本没建**：模型探活 09:10、干活队列清算 10:05、Hermess 待办盘点 11:05 → 需新建 3 个任务，并给两家补脚本执行权限

## 六、验收标准
1. `python3 tools/butler-duty.py` 返回 0（14 项全绿）
2. 群消息里每天能看到 5 家各自署名的实质结论，不是"正常"
3. 连续 7 天没有任何一家因"无产出"被降频
4. 每周日覆盖检查与巡检结论一致

## 七、回滚
删 `state/butler/contracts.json` 与 `tools/butler-duty.py`，移除 12:30 定时器即可，不影响既有 5 个自审任务。

## 八、交叉互审 + 模型分工（v1.1 · 主公 15:10 令）

### 8.1 互审配对
- 果果 ↔ Hermess（果果审 Hermess 的产出与待办；Hermess 审果果的开工清单与账本）
- 维护 ↔ 备份（系统健康 vs 备份产物，互为外部事实）
- 模型 ↔ 干活（模型可用性 vs 任务执行结果）

### 8.2 怎么落地
1. 12:20 由 `tools/cross-audit-pack.sh`（零 token）先把六家事实包刷新，再把「自家 + 对家」拼成一份 `audit-inputs.md` 放进各自工作区
2. 12:25-13:14 各家自审任务改成读这一份文件，输出三段：①自审 ②对家审计（至少 1 条具体质疑，或写明抽验通过的具体项）③明日计划
3. 13:26 汇总时对比两家的说法，出现互相矛盾（如备份说 1 份、维护说 0 份）直接进 20:30 简报红字

价值：单家自审只能证明"我跑了"，互审能暴露"两家看到的事实不一致"——那才是真问题。局限也要说清：这是**对事实包的交叉抽验**，不是深度进对方系统查证；对家事实包本身造假时互审发现不了。

### 8.3 模型分工（每家不同，避免同源同错）
- 维护：zai/glm-5.3-flash
- 备份：deepseek/deepseek-flash
- 模型：kimi-coding/kimi-for-coding
- 干活：qianwen-token-plan/qwen3.8-flash
- Hermess：minimax/MiniMax-M3.1-Flash-Preview
- 果果：不变（deepseek/deepseek-flash 为主）

每家都带两级回退（deepseek-flash / glm-5.3-flash），某个 provider 挂掉自动降级。分工的意义是：一家模型的盲区不会被五家同时继承。
