# B 机渲染农场方案（2026-11-21 夜）

## 一句话
剪辑的"脑子"留在 A（剪辑管家），"肌肉"搬到 B（RX 9070 XT + 9950X），A 侧只多一个白名单脚本 `tools/render-offload.sh`。

## 为什么必须搬（实测，不是猜）
- A 的 ffmpeg 是 johnvansickle 静态构建 7.0.2，`-encoders` 里 **nvenc / amf / qsv 一个都没有** —— 3070 完全没用上，剪辑一直吃 CPU。
- A CPU 编码实测：libx265 medium，1080p60 30 秒素材 → **109 fps（1.8x 实时）**，16.5 秒。
- B 机 GPU 编码实测：hevc_amf quality，同一段素材 → **675 fps（11.2x 实时）**，2.6 秒。
- 结论：**B 比 A 快 6.2 倍**，而且 B 的 CPU 是 Ryzen 9 9950X 16 核（A 是 7900X）。
- B 环境现状：AMD Radeon RX 9070 XT，驱动 32.0.32029.2010；ffmpeg 9.0.2-full（gyan build，`C:\ffmpeg\bin`），AMF 三件套可用：hevc_amf / av1_amf / h264_amf（9070XT 支持 AV1 硬编，AV1 同画质比 HEVC 再省 30% 体积）。
- B 磁盘：C 939G 空闲、D 1582G 空闲。

## 架构（不依赖 node，不怕网关重启）
1. B 的 D 盘共享（`\\192.168.1.107\D`，445 端口已通）挂到 A 的 `/mnt/b`，SMB3 + uid/gid 映射。
2. B 侧常驻 worker：`D:\render\worker.ps1`（已部署，1771 字节），登录自启计划任务 `OpenClaw-RenderWorker`。
3. 队列协议（纯文件，跨机无锁）：
   - `D:\render\queue\<jobid>.json` —— A 写，内容 `{"id":..., "args":[ffmpeg 参数数组]}`
   - worker 取走 → 移到 `work\<jobid>.json`（表示运行中）→ 调 ffmpeg `-progress work\<jobid>.progress`
   - 结束写 `work\<jobid>.done`（rc + 秒数），日志在 `log\<jobid>.log`
4. A 侧唯一入口：`bash tools/render-offload.sh check|submit|status|wait|list`。
5. 剪辑管家仍用 vcut/vsub/vmux 做决策（切点、字幕、混音），只有"编码/转码"这一步发给 B。

## 为什么不用 nodes invoke
- `openclaw nodes invoke` 明确拒绝 `system.run`：「reserved for shell execution; use the exec tool with host=node instead」。
- 而 exec host=node 是工具层能力，不能出现在 shell 脚本里，剪辑管家（deny nodes）也用不了。
- 队列文件方案绕开这个限制：只要 SMB 通，任何管家、任何 cron、任何脚本都能提交任务。

## 回退与容错
- worker 挂了 → `worker.log` 停止更新，编解码任务停在 queue；A 侧可切本地 CPU 编码（慢但能出片）。
- B 关机/断网 → 队列文件留在共享盘上，B 回来继续，不丢任务。
- 编码失败（rc≠0）→ done 文件里带 rc，A 侧自动改走 CPU 重编。

## 实测命令留档
```
# B GPU（1080p60/30s）
ffmpeg -f lavfi -i testsrc2=size=1920x1080:rate=60:duration=30 -c:v hevc_amf -b:v 8M -f null NUL
# → 675 fps, speed=11.2x

# A CPU（同素材）
ffmpeg -f lavfi -i testsrc2=size=1920x1080:rate=60:duration=30 -c:v libx265 -preset medium -b:v 8M -f null -
# → 109 fps, 16.47s
```
