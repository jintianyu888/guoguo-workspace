# 隐私与 PII 处理规范（果果主区 · 2026-10-31 立）

## 起因
2026-10-31，模型管家在跨会话消息中三次明文写出主公手机号；第一次被告知后仍重复两次。号码无法回收，教训必须落成规则。

## 一、什么算 PII（本机口径）
手机号、短信/邮件验证码、身份证/护照号、银行卡、家庭住址、生物特征（人脸/指纹）、健康与病历、账号密码与 API key、私聊原文。

## 二、铁律
1. 不写进跨会话消息。需要转述时只说事实形态，不给值。例：「主公配合完成短信验证，验证码一次性使用、未留存，号码未记录」。
2. 不写进台账、日志、变更单、脚本注释、docstring、commit message。
3. 不进 shell history。传参用环境变量或临时文件（用完即删），不要把号码当命令行参数。
4. 不落明文文件。密钥只进 secret store；一次性凭据不允许存盘。
5. 不复述。对方给了 PII，回复里不得引用其值——即使为了「确认我理解对了」。

## 三、必须做的自查（收到 PII 的一方）
- 号码/验证码是否进过：state/、docs/、cron 日志、~/.bash_history、变更单、台账。
- 登录态是否被导出成 cookie/json 文件，还是只活在浏览器 profile。
- 结论必须给「有/无 + 文件路径 + 处置（已删/在回收站/未动）」，不接受「已注意」「不会外传」这类表态。

## 四、发现违规后的处置顺序
1. 停止传输：立即告知对方停止复述，而不是「下次注意」。
2. 清副本：文件级删除走回收站，留台账。
3. 报主公：谁、传了什么、传了几次、清没清干净，一句话说完。
4. 存证：会话记录无法回收，如实说明，不假装没事。

## 五、授权不等于豁免
即便主公明确要求某操作（如代为登录、代抓余额），PII 仍受本规范约束：
- 一次性验证码用完即弃，不存、不回显。
- 授权依据要落一行台账（谁、何时、什么形式），避免事后「他说过」。

## 六、模型管家补充条款（2026-10-31 并入）
PII（手机号、验证码、身份证、银行卡、住址、密钥）不得进入：跨会话消息、台账/文档、cron 与运行日志、shell 命令行参数、临时脚本。
确需临时使用时只经 stdin 或内存传递，用完即作废，不写入文件、不进入历史、不回显、不落备份；转述一律写「用户已配合完成验证，凭证未留存」。
**自查扫描时也不得把待查明文写进命令或脚本**，须用编码还原或脱敏模式——否则"检查泄漏"这个动作本身就成为新的泄漏点（今晚就发生过：扫描脚本把号码当搜索串写进 /tmp）。

## 七、本机已知残留（如实记录，勿宣称已清除）
- agents/main 与 agents/model 的 openclaw-agent.sqlite（含 -wal），及 agents/main 下 .bak-secmig 备份：含该串，无法在不损坏库的前提下改字节。
- state 下 3 个 pre-startup 迁移备份（约 35MB/127MB/60MB）：sqlite 快照，同样含该串。
- 每日 01:00 全量备份会让该串随备份副本按保留策略自然老化退出。
- 结论口径：**本地副本层面已脱敏到位，会话与备份层面属低危长期存在，不主张为隐私而删备份**（现库仍在，删备份收益为零、却丢回滚材料）。
