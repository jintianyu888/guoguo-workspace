## 七、18789 为何"找不到规则却能连"——已定位（2026-11-12 22:36）

PowerShell 精确查询（Get-NetFirewallRule + PortFilter/AddressFilter）结果：
- 匹配 9443 的入站规则只有一条：**oc-9443，RemoteAddress = 100.64.0.0/255.192.0.0（即 100.64.0.0/10，tailnet）** ✅
- **匹配 18789 的入站规则：零条**。也就是说 18789 不是被自己的规则放行的。

宽口径放行规则共 8 条（LocalPort=Any + RemoteAddress=Any + Allow），其中与本机端口转发最相关的是：
- 连接设备平台(TCP-In) → svchost.exe
- 连接设备平台(UDP-In) → svchost.exe
- 核心网络 - IPv6 (IPv6-In) → System
- Teredo/SSDP、远程协助、Wi-Fi Direct 等

结论（推断，需一次实测确认）：portproxy 的监听属于 iphlpsvc（svchost）承载，
因此 18789 是被上述 svchost 宽口径规则顺带放行的——**关掉它们会连带影响 Windows 功能，不能盲关**。

### 处置口径
1. 现实暴露面：路由器未做 18789 端口映射 → 外网进不来；风险集中在"同局域网内被入侵的设备"
2. 要真正收紧有两条路（都需窗口 + 可回滚）：
   a. 把 portproxy 的 listenaddress 从 0.0.0.0 改成具体 IP（LAN 一条 + tailnet 一条），本机不再监听 0.0.0.0
   b. 为 18789/9443 加"精确 block + 精确 allow"组合，需先实测 svchost 规则是否被覆盖
3. 在没做 a/b 之前，**不声称 18789 已受控**——这是 #997 要收的口

## 八、2026-11-13 19:05 复核：9443 的 tailnet 规则不生效（实测推翻）

### 8.1 哨兵先坏了：假 OK
- `tools/exposure-check.py` 用 gbk 解 netsh 输出，而 netsh 经 WSL interop 出来是 UTF-8。
  → 一条规则也匹配不到，`firewall_open_any` 恒为 `{}`，于是每小时都打印 `EXPOSURE_OK`。
- 已修（2026-11-13 19:02）：utf-8 优先 + gbk 兜底；无任何规则可读时打印 `EXPOSURE_UNKNOWN` 且 rc=2；
  `--selftest` 覆盖「任何IP放行/定向放行/阻止规则/空输出」四种情形；`rules_scanned` 写入 state/work/exposure.json。
- 修后真实扫描：655 条规则；`18789` 命中 0 条、`9443` 命中 1 条。

### 8.2 实测：LAN 上非 tailnet 主机两个口都能打通
- 探测机：NAS（192.168.1.5 / 192.168.1.101，**无 tailscale**，纯 LAN）
- `curl http://192.168.1.108:18789/` → **200**（0.004s）
- `curl -k https://192.168.1.108:9443/` → **200**（0.012s）
- 结论：`oc-9443` 那条「远程 IP=100.64.0.0/10」的放行规则没起收紧作用——portproxy 的监听进程是 svchost，
  Windows 防火墙「任一放行规则命中即放行」，svchost 的宽口径规则把所有端口都盖住了。
  所以原文「9443 已收紧为仅 tailnet 可入」**不成立**，18789 同样对 LAN 敞开。
