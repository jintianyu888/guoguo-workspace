# 管家效率与轮值互审机制 v1.0（2026-11-06 主公批）

> 目的：提高四大管家（maint/backup/model/work）的产出质量与执行闭环，用数据决定留用，不搞双执行互撞。
> 真源：本文件为规则真源；评分数据落在 state/approvals/proposals.jsonl 与 state/work/steward-score.jsonl。

## 一、为什么不搞「双管家同岗竞争」
管家会写台账、改配置、发告警、跑脚本。两个同时干同一件事必然出现：重复告警、文件互相覆盖、抢锁打架（2026-11-06 面板被 selfheal 拉起抢句柄导致切换中止即为实例）。竞争改为「只读影子/互审」形式，永远只有一个执行者。

## 二、每周轮值互审（零成本，先跑四周）
- 周期：每周一 20:30 由 main 派发，周日 20:30 前交报告。
- 轮换：maint→审 backup；backup→审 model；model→审 work；work→审 maint（每周轮转，四周一轮）。
- 约束：互审者**只读**，不许改配置、不许发告警、不许动文件；发现的问题只写报告。
- 报告落盘：/home/j/openclaw-workspaces/<被审管家>/inbox/YYYYMMDD-<审者>-peer-review.md，同时交 main。
- 互审本身也计分（见四）。连续两周不交 = 该管家黄牌。

## 三、自审/周报硬模板（缺项直接退回，不计交付）
每条建议必须四要素齐全，否则视为无效建议：
1. 问题（一句话）
2. 证据（file:line 或命令+输出行）
3. 建议动作（可执行到命令级）
4. 验收标准（改完怎么证明好了）
外加：级别 P0（服务不可用/数据风险）/ P1（性能、容量趋势）/ P2（优化项）。

交付定义：报告文件落盘 + inbox 通知 main。只有聊天里说了不算交付。

## 四、评分表（满分 100，四周一次结算）
- 交付率 30：应交次数中按时交的比例
- 有效发现 25：被确认属实且此前无人提出的问题数（main 复核）
- 可执行性 15：四要素齐全率
- 落地率 15：建议被批准后 48h 内执行的占比
- 零事故 10：该域当期是否发生可归因事故
- 互审质量 5：作为审者发现的问题是否属实
红线：P0 项连续 3 天重提而无结论 → 自动升级到主公，且该管家当期封顶 60 分。

## 五、批复闭环（当前最大堵点）
- 所有建议进 state/approvals/proposals.jsonl（tools/steward-proposals.py 维护），有唯一 id、状态、首次提出时间、重提次数。
- 状态：new / approved / rejected / deferred / done。只有 main 能改 approved，提案与批准分离。
- P0：48h 内必须有结论；P1：7 天；P2：进半价窗队列。
- 每日 08:45 出摘要：新增、超期、重提、待主公拍板四类，一条一结。

## 六、效率红线（防止自审把系统拖慢）
- 自审/周报期间禁止跑 >2 分钟的重活、全盘扫描、批量写。
- 同一管家同期只允许 1 个评审任务在跑，禁止并发堆叠。
- 报告正文 ≤ 200 行，超出改为「摘要 + 附件路径」。
