## 3. 现有「归档」是怎么实现的，为什么只压掉 7 天

### 3.1 命令行层面

```
openclaw sessions archive <keys...> [--dry-run] [--json]
openclaw sessions compact <key> [--max-lines N] [--json]
openclaw sessions cleanup [--active-key ...] [--all-agents]
```

对第 1 名会话跑 `sessions archive --dry-run` 返回：
`{"status":"would_archive"}` —— **archive 是"整会话归档"，只改可见性/保留元数据，不删事件、不降事件数**。

### 3.2 事件确实被删过（这是关键证据）

- `transcript_events` 本会话 seq 范围 = **36,213 … 62,753**，行数 26,541。
  ⇒ seq 是**按会话**计数（其他会话都从 0 起），所以**前 36,212 条真实事件已经不存在了**。
- 会话窗口 `session_windows` 创建时间 = **10-17 11:01**，而现存最早事件 = **10-25 01:33** → 丢掉的正好是 10-17 到 10-25 这一段。
- `session_transcript_archives` 中**查不到任何属于本会话的归档行**（全库 375 行全是别的小会话，reason 全为 `deleted`，blob 合计仅 10MB，单个 1–120KB）。
  ⇒ **被删的 36,212 条没有冷备，属于已发生的静默数据丢失。**
- `transcript_rewrite_watermarks` 有本会话一行，`updated_at` 与最新事件同一时刻（持续重写）；
  `session_transcript_index_state` 记录 `max_seq=62,753 / active=62,748`，而实际行数只有 26,541 → **活跃索引虚胖 3.6 万条**（索引未随删除收缩）。

### 3.3 为什么基线不降

1. 归档/压缩只处理**已被摘要覆盖**的历史（10-17～10-25 那 3.6 万条）；摘要前沿之后的原始事件（10-25 至今）原样保留。
2. 最近 7 天刚好产出 26,541 条 → 折叠完还是 2.6 万。
3. 删除不回收空间也不减索引，**事件数只由"会话内未折叠事件的条数"决定**，与库大小、VACUUM 无关。
4. 默认 `session.maintenance` 未配置（`openclaw config get session.maintenance` → unset），运行时用文档默认：`pruneAfter=30d`、`archiveDashboardAfter=7d`、`maxDiskBytes=10gb`、coldStorage 未开。
   **7 天这个数字在 det 代码里没 grep 到对应常量，确切触发点：查不到**（能确认的是"这次删除发生在 10-25 01:33 前后、未留归档"）。

## 5. 三个「永久解决」候选方案

### 方案 A｜会话生命周期：定长轮换 + 归档冷存（治本，推荐先做）

- **改什么**
  1. 规则：在 `AGENTS.md`/新会话规则加硬线——「本会话事件 ≥15,000 或满 3 天，必须先把任务落盘到 `state/tasks/tasks.json`，再 /new」。
  2. 监控：改造现有 cron `会话体积巡检(10m)`（job id `594a1453-ae46-424b-b584-1732561c9b02`）+ `tools/session-health-watch.py`：除 token 外直接查 `transcript_events` 计数（`mode=ro`），≥14k 告警、≥18k 升级。
  3. 旧会话退场：`openclaw sessions archive <key>`（dry-run 已验证可用），导出的 `*.jsonl.deleted.*.zst` 进 NAS 冷备。
- **预期效果**：新会话从 0 起；按日均 3.7k 计算，3 天 ≈ 11k，**稳定落在 6k–12k**，永不触 20k。
- **代价**：每 2–3 天要 /new 一次；旧会话从会话列表消失（.zst 可找回，但不在 UI 里）。
- **风险**：/new 前进度没落盘 = 丢上下文；归档后旧会话不可在 UI 检索。
- **回滚**：归档只改可见性，可用 `openclaw sessions` 恢复/导出；删掉规则段落即可。
- **验证**：新会话 `select count(*) from transcript_events where session_id=? ` 从 0 起；`seq` 归零；`/status` 事件数下降。

### 方案 B｜数据保留策略：显式 maintenance 配置 + 一次性 VACUUM

- **改什么**
  1. `openclaw config set session.maintenance '{"mode":"warn","pruneAfter":"4d","maxDiskBytes":"2gb","coldStorage":{"enabled":true,"afterDays":2}}'`（先 warn 观察一周，再 enforce）。
  2. 维护窗对 agent db 做一次 VACUUM（回收 ~116MB），复用 `tools/lcm-maintenance.sh` 的条件 VACUUM 逻辑，**不要动 lcm.db**（只剩 1.6MB）。
- **预期效果**：4 天窗口 → 事件数稳定在 **~15k**（日均 3.7k×4）；agent db 684MB→约 568MB；lcm.db 无变化（784MB 降不下来，除非裁 message_parts）。
- **代价**：4 天前原始事件更快被折叠，可回溯窗口从 7 天缩到 4 天；摘要质量成为唯一历史来源。
- **风险**：`pruneAfter` 设太短会连活跃会话正在用的历史都折叠；enforce 模式下手滑不可逆（warn 模式只报告不改）。
- **回滚**：`openclaw config unset session.maintenance` 回到默认（30d）；VACUUM 不可逆但不丢数据。
- **验证**：warn 模式日志里看"将删除 N 条/多少个会话"；一周后对比 `transcript_events` 行数与 `freelist_count`。

### 方案 C｜配置与工程：把每轮事件数与每事件字节压下来

- **改什么**
  1. lossless-claw（`plugins.entries.lossless-claw.config`，现值：`contextThreshold 0.1`、large-context 覆盖 `0.15`、`freshTailCount 16`、`leafChunkTokens 12000`）→ 调成 `contextThreshold 0.25`、`freshTailCount 32`、`leafChunkTokens 20000`：减少压缩频率与摘要碎片。
  2. 工具输出入库裁剪：tokenjuice（已启用）调低单条 tool_output 上限，目标把 43.1MB 的压缩工具体砍到 15MB 以内。
  3. `tools/session-health-watch.py` 增加事件数与 MB 双维度（现在只看 token 160k/180k）。
- **预期效果**：字节 74MB → **<20MB**（达标）；每轮事件 14.4 → 8–10（custom 进度事件收敛），同样 3 天 ≈ 6k–8k 条。
- **代价**：压缩变少 → 长会话更容易顶到模型窗口（当前 deepseek 上下文线）；工具输出被截断，排障细节变少。
- **风险**：`contextThreshold` 调高可能触发"超窗 → 单次请求失败"；tokenjuice 截断过头会丢报错原文。
- **回滚**：三处 config 都是单值，改回 0.1 / 16 / 12000 即可（现值已在本报告留档）。
- **验证**：连续 3 天采样「事件数/轮」「MB/轮」；`/status` 里 context tokens 不越线。

**建议顺序**：A（今天就能见效、零风险）→ C（一周内调参，压字节）→ B（观察一周 warn 后再 enforce）。
