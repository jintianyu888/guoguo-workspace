# 会话卫生与事件循环保护规则 v0.2（2026-11-01）

> v0.1 被 minimax/MiniMax-M3 否决（REJECT，8399B）。否决要点：把"定期归档"当主手段方向错了，
> 根治应是**读取路径有界化**；且"不再添加工作""迁移活动会话""避免误杀"三处没有可执行机制。
> 本版重写：主手段改为压缩阈值控制 + 会话冻结，归档降为兜底。

## 一、病因分级（据实测）

**直接阻塞点**：主 agent SQLite 的 `session context snapshot read`，async=false，同步执行。
1 小时触发 10 次，每次持锁数十秒，事件循环随之停摆（实测 90.5s / 76.2s）。

**放大机制**：单会话无界增长到 62,407 事件 / 122.8 MB（全库 127,168 行），
使得本来可能只花毫秒级的快照读变成分钟级。没有这个体量，同步读不会演变成停摆。

**结论**：两者都要治。只治体积不治同步读，同样的量还会再来；只治同步读不治体积，
等于把炸弹留在地板上。本方案对两者分别处理。

## 二、根治手段（按优先级）

### P1 读取路径有界化 —— 压缩阈值收紧
现有配置无 compaction 段，走默认 `keepRecentTokens=20000`。
改为显式配置并收紧，使每次加载的近期窗口受控：

```
agents.defaults.compaction = { enabled: true, keepRecentTokens: 12000 }
```

依据：OpenClaw 压缩在保留近期 token 之外的部分做摘要，读取走摘要而非全量事件。
体积越大压缩越重要；阈值不收紧，摘要永远追不上增长速度。

风险：阈值过紧会丢细节。对策：先 12000 观察 3 天，看是否需要回调到 16000。

### P2 重活外派 —— 子代理独立会话
子代理各自开独立会话，事件不堆进主会话。主会话只保留结论级信息。
这条路同时缓解"主会话体积"和"单次快照读成本"两个指标。

### P3 会话冻结 —— 硬阈后的原子动作
新增 state/session-freeze/<session_id>.lock。写入即视为该会话禁止再派重活。
检查点两处：果果派活前自检；tools/session-hygiene.py 每日扫描时复检。
不自动删任何数据，冻结只约束"新增工作"。

### P4 归档兜底 —— 只对非活动会话
非活动会话（最近写入 >24h）且超硬阈：先导出 JSONL.gz + sha256，校验通过后在事务内清理。
活动会话（24h 内有写入）**永不自动清理**，只告警。

## 三、硬阈值

| 指标 | 软阈（告警） | 硬阈（冻结 + 建议新会话） |
|---|---|---|
| 单会话事件数 | 14,000 | 20,000 |
| 单会话载荷 | 14 MB | 20 MB |
| 事件循环单次停摆 | 30 s | 60 s 连续 ≥2 次 |
| 并发评审单元 | 2 | 禁止 >2 |

## 四、回答三轮否决的三个问题

1. **"不再添加工作"如何原子化**
   冻结靠 lock 文件，不靠自觉。果果每次派活前检查该会话是否有 .lock；有则拒绝派活并转新会话。
   hygiene 脚本每日复检并把违规写进报告。违反即视为流程故障，进账本。

2. **活动会话如何迁移**
   不迁移、不改写。新会话承接后续工作，旧会话置只读冻结，历史保留供检索。
   避免"迁移一半状态丢失"这类事故。

3. **如何避免误杀活动会话**
   双重保护：以最近写入时间为准，24h 内有写入一律不清理；当前会话 id 直接进白名单，最高优先。

## 五、实施步骤

步骤 1（只读，先做）：tools/session-hygiene.py + 每日 03:00 timer，只统计只告警，不动数据。
步骤 2（配置，双审后）：compaction 阈值显式化并收紧到 12000。
步骤 3（机制，双审后）：冻结 lock 机制上线，派活前自检。
步骤 4（兜底，最后）：归档脚本，仅非活动会话，先副本演练。

## 六、回滚

步骤 1：删 timer 与脚本。
步骤 2：恢复 openclaw.json 备份（改配置一律先备份）。
步骤 3：删 state/session-freeze 目录即解除全部冻结。
步骤 4：从 state/session-archive 导回。

## 七、验证

连续 3 天：hygiene 报告无硬阈告警；事件循环停摆 <2 次/小时；模型调用无排队超时。
三条同时满足才算生效。
