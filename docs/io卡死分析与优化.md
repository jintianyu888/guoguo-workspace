# IO 卡死（D 状态）排查 · 原因 · 优化方案

> 2026-10-05 主公令：查并记录所有 IO 卡死进程代码、分析原因、找优化方案。

## 一、现状体检（2026-10-05 13:09）
- D 状态（不可中断 IO）进程：**0 个**；僵尸进程：0
- 负载：0.92 / 0.42 / 0.26；vmstat 的 b（阻塞）列 = 0；wa（IO 等待）= 0
- 结论：**此刻系统 IO 健康**，没有正在卡死的进程。

## 二、风险源（为什么会 D 卡死）
WSL2 里 **C:/D:/E:/F:/G:/H: 六个 Windows 盘全部是 9p 挂载**（/mnt/*）。
9p 不是本地盘，是「Linux 内核 ↔ Windows 主机」的协议转发：
- 任一环节卡住（Windows 磁盘忙/休眠/掉盘、杀毒实时扫描、Windows 侧关机或睡眠、网络盘）→ Linux 侧进程进入 **D 状态**。
- D 状态 = 进程在等内核 IO 返回，**连 kill -9 都杀不掉**，只能等 IO 返回；严重时整机像卡死。
- 高危操作：大文件 tar/rsync 直接读写 /mnt/*；全盘 find/du 扫 /mnt/*；备份写 /mnt/d·e·h；Windows 侧磁盘临时不可用。

## 三、记录器（已上线，零 token）
- 脚本：`tools/io-stuck-watch.py`
  - 每 5 分钟扫描 /proc，抓 D 状态进程
  - 记录：pid / ppid / comm / cmd（进程命令=你说的"进程代码"）/ wchan / **内核栈**（/proc/PID/stack）
  - 追加到 `state/io-stuck.log`；同一进程 D 状态持续 **≥120 秒** 才告警（避免误报）
  - 静默窗口（04:00–05:00）内只记不报
- 定时任务：「IO卡死记录(io-stuck)」cron `*/5 * * * *` · command · announce→飞书
- 台账：`state/io-stuck.log`

## 四、优化方案（按优先级）
1. **热数据留 ext4**：工作区/临时/打包先在 /home（ext4/vhdx 上）完成，再**整份**拷到 /mnt/*；减少 9p 上的高频小 IO。
2. **大 IO 串行**：同一时间只做一个 /mnt/* 大操作（tar/rsync/备份），别并行抢 9p。
3. **加超时**：rsync 用 `--timeout=60 --contimeout=30`；tar 别在 /mnt 上直接读大量小文件。
4. **避开 Windows 休眠**：确保目标盘不休眠；04:00–05:00 断网/关机窗口**别排 /mnt 大活**。
5. **NAS 用软挂载**：若走 NFS/SMB，加 `soft,timeo=50,retrans=2` 之类，避免无限死等（当前备份走 ssh+cat，问题不大）。
6. **监控**：D 进程持续 ≥120s 告警（本次已建）；页脚/台账可见「卡住」态。
7. **频繁 D 就去查 Windows 侧**：事件查看器 + 磁盘 SMART + 杀毒排除项（把 /mnt 对应盘加入杀毒白名单/排除扫描）。

## 五、长期
- `state/io-stuck.log` 会累积卡死样本；若某类进程反复出现，按样本定位到具体脚本再优化。
