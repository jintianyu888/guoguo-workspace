# 重启与升级流程制度 v0.1（2026-10-31 草案，待双审）

> ⏰ 时刻与窗口以 docs/时间表与窗口规则-20261031.md（唯一真源）为准；本文只讲流程，不复述时刻。

## 0. 为什么要改
现有链路能跑，但历史故障反复出在同一批点上：
1. **发起者=被执行者**：agent 自己重启会连会话一起被杀，无法验收、无法回报（10-26 误触 25 秒生产重启即此类）。
2. **入口太多**：restart-gateway.sh / safe-restart-gateway.sh / desktop-rescue.sh / oneclick-rescue.sh / 果果助手按钮 / 定时窗口，语义与检查项各不相同。
3. **升级与重启耦合不清**：`.upgrade-running` 只在 restart-gateway 里检查；升级完成后没有强制校验配置与模型链。今天删模型后 29 处兜底指向已删模型，就是这个缺口。
4. **验收标准不全**：目前只有 新 PID + HTTP 200，缺「配置可解析 / 模型链可达 / cron 恢复 / 重启队列重拉」。
5. **回滚只有备份，没有决策路径**：pre-upgrade-backup 会备份，但失败后谁决定回滚、怎么回滚，没有写死。
6. **记录不全**：重启原因、变更项、验收四项结果未强制入台账，事后无法复盘。

## 1. 五个阶段 + 三道闸

### 阶段 0 提议（任何人有提议权，无执行权）
- 主公口头/飞书指令，或果果/管家提议。
- 统一登记：重启 → `state/work/restart-queue.md`；升级 → `docs/升级台账.md` 新建条目（版本、原因、回滚点）。
- **管家一律不得执行重启或升级**；maint 只做看守与验收。

### 阶段 1 双审（闸 A：制度/脚本改动、版本升级必过）
- 两家不同厂商模型，真跑完（rc=0 且输出 >80 字节，空输出=没跑必须重跑），结论进 `docs/交叉验证台账.md`。
- 高危升级（跨大版本）三审。
- 评审材料必须含：改动文件全文或 diff + 验收标准 + 回滚方式。

### 阶段 2 预检（闸 B：fail-closed）
执行前必须全绿，任一 FAIL 即取消并飞书告警：
- `tools/pre-restart-check.sh` 13 项（进程/端口/内存/磁盘/备份新鲜度/时钟等）
- 冲突检查：`.upgrade-running`、备份静默窗（04:00–06:05）、升级进行中、备份正在跑
- **模型链体检（新增）**：配置中所有 model/fallback 引用必须同时存在于 provider registry 与 B 机 `/api/tags`，悬空即 FAIL
- 备份新鲜度：最近一次全量备份 < 24h

### 阶段 3 执行（闸 C：唯一入口，网关外）
- 入口唯一：`bash tools/restart-gateway.sh --reason "..."`；禁止裸 systemctl / gateway.restart / 桌面按钮直连。
- 由 `systemd-run --user` 提交 `safe-restart-*` 单元，网关不参与执行，agent 掉线不影响。
- safe-restart v5 顺序：写 result(开始) → 停止 → 启动 → 健康探针（HTTP 200）→ 四项验收 → 写 result(结束)。
- 同一时间只允许一个 safe-restart 单元（flock）；`.safe-restart-running` 超 10 分钟视为陈旧自动清理。

### 阶段 4 验收（maint 维护管家执行，四项全绿才算成功）
1. `systemctl --user is-active` = active 且 PID 变化
2. `GET /health` = 200（3 次重试）
3. **模型链 smoke**：`local` 别名一次最小请求成功 + 配置解析无悬空引用
4. **任务恢复**：cron 列表可读、重启队列重拉、无 stuck 任务
任一红 → 立即飞书告警 + 标记「重启不完整」→ 主公决定回滚或人工介入。

### 阶段 5 记录
- 每次重启/升级必须写：原因、变更、四项验收结果、耗时、结论。
- 失败必须写复盘，存 `state/work/restart-postmortem-<日期>/`。
- 台账：`docs/重启升级台账.md`（新增，一行一次）。

## 2. 升级专用流程
1. 提议 + 双审（跨大版本三审）
2. `tools/pre-upgrade-backup.sh "说明"` 必须成功（失败即终止）
3. 打配置快照：`cp ~/.openclaw/openclaw.json state/backup/openclaw.json.bak-<时间>`
4. 写 `.upgrade-running` 标记（阻断并发的重启与备份暂停）
5. 升级执行：**只由主公/操作员**在终端执行 `openclaw update`（agent 禁止执行）
6. 验收：`tools/upgrade-acceptance.sh`（现 12 项）+ 模型链体检 + 配置读回核对
7. 清理标记 → 按阶段 3 重启 → 阶段 4 验收 → 阶段 5 记录
8. 失败回滚：恢复 `openclaw.json` 快照 + 按备份恢复数据 + 版本回退指令（写入台账条目）

## 3. 与果果助手的整合（三分区）
- **查看区**：网关状态、最近一次重启 result.json、升级状态、重启队列条数
- **办事区**：申请重启（只写队列，不执行）、申请升级（只登记）、查看制度
- **维护区**：一键自检（只读）、查看上次验收、导出诊断包；「立即重启/立即升级」保留二次确认 + 必填原因 + 最终仍走 `restart-gateway.sh`，**禁止直连 systemctl**

## 5. 风险与代价
- 预检变多会让重启变慢 20–40 秒（可接受，重启本来就不该快）。
- 模型链体检依赖 B 机可达；B 机离线时该项记为 WARN 而非 FAIL（否则断网时无法重启，形成死锁）。
- 回滚能力仍受限于备份恢复速度（约 20–40 分钟），不承诺秒级。
