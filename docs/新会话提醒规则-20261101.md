# 新会话提醒规则 v1.1（2026-11-01 主公令）

> 主公令：「在适当的时候提醒我 /new，每个管家都要有这个规则」
> 适用：果果（main）＋全部管家（四大管家 + 全部业务助手）
> 落地：各工作区 AGENTS.md 顶部强制块 `<!-- NEW-SESSION-RULE:v1 BEGIN/END -->`（脚本幂等注入，勿手改）
> 本文件为唯一真源。v1.1 由工具 deepseek/deepseek-v4-pro + kimi-coding/k3-256k 双审后收敛（两路均真跑完并提修改意见，无否决）。

## 一、为什么（根因）
单会话 14k 事件/14MB 告警、20k 事件/20MB 冻结；上下文被压缩后细节会丢，带着损耗的记忆继续判断，越做越错。
主动 /new 比被动冻结便宜得多。

## 二、什么时候提醒（满足任一条）
### A. 可测信号（优先，估不准就不报数字）
1. 收到会话体积告警（14k 事件/14MB）或冻结（20k/20MB）→ 立刻提醒并建议马上 /new。
2. /status 或运行时明确显示累计 token ≥ 120k（lossless 自动压缩线 150k 之前）→ 提醒。
3. **拿不到数字时用「轮次 + 时长 + 话题」判断，不许编造 token/事件数。**

### B. 语义时机（看见就提）
4. 长任务交付收尾、且该任务已跨 5 轮以上。
5. 话题切换：新请求与当前会话主题无关（运维↔作曲↔选题等）。
6. 同一件事来回 ≥ 20 轮，或单会话连续工作 ≥ 60 分钟（起算＝本会话首条消息至今）。
7. 准备开重活前（长扫描、批量写、大迁移、多轮评审）——先开干净会话再做。
8. 发现上下文已丢细节（重复问同一件事、引用错之前的结论、记不清路径/数值）。

## 三、提醒格式
一句话 + 一句续用建议，≤3 行，单独成段，不埋进正文：
```
💡 建议 /new：本会话已 X 轮／约 Y token（或：任务已收尾／要换话题了）
新会话第一句：「继续 <任务/账本 id>，上次到 <状态>，下一步 <动作>」
```

## 四、先落盘再建议（硬要求）
提醒前必须把「任务 id／当前状态／下一步」写进账本（state/tasks/tasks.json）或对应 state 文件，
并在提醒里给出位置。**没落盘不许建议 /new**——否则新会话接不上，等于丢活。

## 五、频率与克制
- 同一会话最多 3 次；两次间隔须**同时** ≥15 分钟且 ≥10 轮（AND，防止刷屏）。
- 主公说「不用 /new」「先这样」后：本会话不再提（除非 20k/20MB 冻结硬线）。
- 刚 /new 后前 5 轮不提；主公紧急排查/单步操作中不提，等该动作结束再提。
- 单问单答、闲聊、查一个值（1–2 轮）不提。

## 六、不适用
- cron、心跳、子代理、批处理等**无人值守**会话不提醒（没有主公在场）。
- 本规则只管「有人值守的交互会话」，各管家只对自己会话提，不替别人的会话操心。

## 七、责任分工
- 各管家：自己会话自己提。
- 果果：每日盘任务时看一遍各会话体积，超标的下发提醒；新接入管家一律注入本块。
- 维护管家（maint）：只读巡检发现硬指标超标 → 告警，不替人 /new。
